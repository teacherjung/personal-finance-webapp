## 1. 模組互相引用，載入當下就讀對方的值

### 適用條件

- JavaScript，用 import／export 或 require 把程式拆成模組。
- 模組之間有循環引用：A 引 B，B 直接或繞一圈又引回 A。
- 而且有模組在載入當下讀循環另一端的值。
- 載入當下包括：檔案最外層的讀取、最外層就呼叫的函式裡的讀取、類別的 static 欄位。
- 只在載入完成後才被呼叫的函式裡讀的，不適用。
- 例外：CommonJS 的對方用 `module.exports = …` 整個換掉時，函式裡讀的也適用。它手上的還是換掉前那個舊物件。

### 會怎樣

本機實測：

- ES 模組（import／export）讀到對方還沒跑到的值，當場丟錯（ReferenceError）。對方用 const、let、class 宣告的，或 `export default` 後面接運算式的（物件、箭頭函式、class），都會。
- 先用 `typeof` 檢查，一樣丟錯。
- 從靜態入口載入時，引到它的那一串都不會跑，程式以退出碼 1 結束。用 `import()` 動態載入時，錯誤交給那個 Promise：呼叫端接住拒絕（`.catch`、`try`＋`await`）程式才不因這個錯結束；沒接住，照樣以退出碼 1 結束（Node 26.0 實測）。改用動態載入不等於把錯誤隔離開。
- ES 模組讀到對方用 var 宣告的：拿到 undefined，不丟錯。
- ES 模組叫對方用 function 宣告的函式（含 `export default function`）：函式本身叫得動。但它裡面讀到自己模組還沒跑到的 const、let、class，一樣丟錯。
- CommonJS（require）：對方還沒跑到設定那個屬性的那一行，就拿到 undefined，不丟錯。
- CommonJS 用解構（`const { X } = require(…)`）拿到的 undefined，之後也不會變。要到呼叫時才丟 TypeError「X is not a function」，離原因很遠。
- CommonJS 的對方最後用 `module.exports = {…}` 整個換掉：載入完成後才在函式裡讀，一樣丟 TypeError「a.X is not a function」。
- CommonJS 的警告：對方的 module.exports 是普通物件時，讀到還沒設的屬性，Node 另印一行「Accessing non-existent property … inside circular dependency」。對方先把 module.exports 換成函式時，不印。
- CommonJS 讀到對方先設、之後才改的屬性：拿到舊值，不丟錯，也不印警告。

原專案 #244 的合併提交說明寫：在瀏覽器裡是整個 app 停在「載入中」。

### 怎麼查

- 新加的載入當下讀取，追它的來源會不會繞回自己。
- 載入當下就要用的共用值，放進一支相依裡不會繞回來的檔（最好什麼都不引用），直接引它。不經會引回來的總入口轉手。
- 其餘的讀取，留到載入完成後、函式被呼叫時才讀。
- 從正式入口實際載入一次。伺服器就啟動一次；瀏覽器見下面那條。
- CommonJS：跑一次，看有沒有上面那行警告。跑的時候不帶 `--no-warnings`、不設 `NODE_NO_WARNINGS`，這兩個會把警告關掉（本機實測）。
- 讀到舊值、對方把 module.exports 換成函式時，都不印。所以沒看到警告，不代表沒有循環。
- 有瀏覽器端程式、前端有改動時：用隔離資料（規矩 B4）把每一頁在瀏覽器實際載入一次，主控台沒有錯誤。
- 頁面清單從程式自己的路由表取，不寫死頁數。

### 考題守不到

- 考題直接引新模組時，循環裡誰先跑，可能跟從正式入口進來不一樣。正式入口會壞，考題照樣綠（本機實測：從總入口進來丟錯、退出碼 1；考題直接引那一支，1 題全綠）。
- 瀏覽器端模組一載入就碰畫面時，在 Node 裡跑、又沒有模擬畫面環境的考題載不進它。考題全綠，瀏覽器照樣可能整頁開不起來。
- 原專案 #244 那一次是瀏覽器載入檢查抓到的，不是考題。

## 2. 把資料拼成 HTML 字串

### 適用條件

- JavaScript 用字串把資料組成 HTML，再交給頁面（例如 innerHTML、insertAdjacentHTML）或寫成 HTML 檔。
- 而且資料有任何一段不是寫死在程式裡：使用者輸入、匯入檔、備份還原、外部服務的回應、資料庫裡的舊資料。
- 只放純文字的寫法（例如 textContent），不適用。
- 交給會自動跳脫、又沒開「原樣插入」的範本工具，不在這一節的範圍。

### 會怎樣

- 一段 `"><img src=x onerror=…>`，在雙引號屬性裡會提前關掉屬性，在一般文字裡直接開出新元素。兩處都變成真的 img 元素（本機實測）。
- 原專案 #313 的說明寫：在修之前的主幹上，用隔離的合成資料庫重現，payload 真的執行（頁面上出現兩個真的 img）。修好後 10 頁都沒有。
- 它存在資料裡，每次開那一頁都再跑一次。
- 它用那一頁的身分跑：那一頁讀得到的資料，包括「機密」，它都讀得到。這一句是原專案 #313 說明的推論，沒有實際被利用的紀錄。
- 下面四種位置，跳脫了照樣會出事（本機實測）：
  1. 單引號屬性，跳脫函式沒處理 `'`：上面那串不會變成元素，看似沒事。換成 `x' onclick='…`，點一下就執行。
  2. 沒加引號的屬性：`&`、`<`、`>`、`"`、`'` 全跳脫了，`x onclick=…` 還是變成一個新屬性，點了會執行。
  3. onclick 這類事件屬性：五個字全跳脫了，`');…;('` 照樣執行。屬性值會先被解回原字，再當程式跑。打上面那串反而不執行。
  4. href：`javascript:…` 跳脫後原封不動。只量到值沒變；點下去會執行，是推論的。

### 怎麼查

- 共用的跳脫函式只管兩個位置：HTML 的一般文字，和加了雙引號的普通文字屬性（例如 title、alt、value、data-）。這兩個位置的每個插值點都過它。
- 看起來是程式產生的值（例如 id）也算。備份還原、匯入有可能把任意的字帶進來；原專案 #313 就是備份裡的 id。
- 跳脫函式要處理 `&`、`<`、`>`、`"`、`'` 五個字。
- 屬性值一律加雙引號。
- 資料不放進 onclick 這類事件屬性、`<script>` 裡的程式碼（含樣板字串）、style，也不放進會再被當成 HTML 解析一次的屬性（例如 iframe 的 srcdoc：外層先把跳脫解回原字，再把那段當 HTML 解析，五字跳脫擋不住；複審者在瀏覽器實測）。非放不可時，照那個位置自己的編碼規則處理（OWASP 的 XSS 防範速查表依位置分列），不拿五字跳脫當放行的依據：五字跳脫不動 `${…}` 這類字，資料放進內嵌程式碼的樣板字串照樣會被執行（原專案沒有這類事故；這一點是複審時用 Node 實測的）。
- 放進 href、src 這類網址屬性時，另外只放行認得的開頭（例如 http、https）。這一條是推論的預防。
- 跳脫函式全專案只留一份實作。考題直接引用正式那一份，不另抄一份。這一條是推論的預防：原專案 #409 的說明寫，抄出來的會漂。
- 挑一個插值點，用隔離資料（規矩 B4）把值換成上面那串，在瀏覽器打一次。畫面要顯示成文字。
- 那一串只證明雙引號屬性與一般文字。單引號屬性另打 `x' onclick='…` 那一種。

### 考題守不到

- 掃原始碼找「沒跳脫的插值」的考題，只守它認得的那幾種寫法。換一種寫法，照樣綠（原專案 #340 的說明寫過同型的原始碼考題：換一種寫法照樣全綠）。
- 這種考題的「註解」寫它認不得的寫法（擋不住什麼；規矩 K3）。
- 瀏覽器端模組在 Node 裡載不進來時（見第 1 節），畫面那一端沒有行為考題，只剩讀碼與瀏覽器實測。

### 出處

- 原專案 #13（2026-07-11）<https://github.com/teacherjung/personal-finance-webapp/pull/13>：一頁的訊號值漏跳脫。修後實測注入 payload，顯示成純文字、不執行。
- 原專案 #313（2026-07-28）<https://github.com/teacherjung/personal-finance-webapp/pull/313>：備份檔裡的 id 原樣保留，進了 HTML 屬性卻沒跳脫。說明寫：對整個倉庫重新檢查時抓到，另外再獨立核一次確認。
- 原專案 #409（2026-08-06）<https://github.com/teacherjung/personal-finance-webapp/pull/409>：跳脫函式搬成一支獨立的檔，不抄第二份。

## 3. 使用者或外部文字當物件的鍵

### 適用條件

- JavaScript（瀏覽器或 Node）。
- 拿使用者或外部文字（名稱、備註、匯入檔的欄位）當普通物件的鍵：對照表、別名表、聚合加總、查表、遞迴合併、依路徑寫值（a.b.c）。
- 改用 Map，或鍵只來自程式寫死的清單，不適用。

### 會怎樣

本機實測：

- 讀 `m['__proto__']`，拿到的是所有普通物件共用的那個原型。在它上面寫一個欄位，同一個執行環境裡一般的物件都讀得到；沒有原型的物件讀不到。
- worker_threads、vm 開的新環境各有自己的原型，看不到那個欄位。瀏覽器的 iframe 也一樣，這一點是推論的。
- `m['__proto__'] = 物件` 不會建鍵，而是換掉 m 的原型：`Object.keys(m)` 和轉出來的 JSON 裡都沒有它。
- 指派 null 會讓 m 變成沒有原型的物件。之後轉字串（`String(m)`、樣板字串）會丟 TypeError。指派其他原始值，直接被忽略。
- 鍵是 `toString`、`constructor` 這類名字時，查表撈到原型上的函式。
- 簡單的遞迴合併吃進 `JSON.parse('{"__proto__":{"polluted":"yes"}}')`，同一個執行環境裡的普通物件都多了 polluted。

原專案的說明寫的後果：

- 全域原型被寫進一個欄位後，下一次載入 PDF 解析函式庫就崩潰（原專案 #139 的說明，貼了錯誤訊息）。
- 把分類改名成 `__proto__`：舊名刪了、新名沒存、儲存回報成功（原專案 #146 的說明）。

### 怎麼查

- 查表只認自有的鍵（`Object.hasOwn`）。
- 寫入與聚合用沒有原型的物件（`Object.create(null)`）或 Map，或先拒收保留字。
- 在普通物件上先用 hasOwn 檢查再寫，不夠：鍵是 `__proto__` 時，照樣換掉原型、鍵也不見（本機實測）。
- 光靠沒有原型的物件也不夠，讀、寫兩端都要守（本機實測）：
  - JSON 來回一趟，它就變回有原型的普通物件。
  - 用 `Object.assign` 拷進普通物件時，`__proto__` 被當成換原型：鍵不見了，拷貝卻繼承了輸入裡的欄位。輸入是 `{"__proto__":{"isAdmin":true}}` 時，拷貝的 isAdmin 是 true。
  - 用展開 `{...}` 或 structuredClone 拷貝，會留成自有鍵。
- 特別看這三種寫法（原專案 #150）：
  1. `m[k] ||= {…}`：鍵是 `__proto__` 時，讀到的原型是真值，不重新賦值，接著就在全域原型上累加。鍵是 `constructor` 時，累加寫在全域的 Object 函式上（本機實測）。
  2. 把使用者的鍵組進普通物件，再轉 JSON 送出：`__proto__` 在送出前就不見了。收的那一端的拒收防線收不到東西，畫面還說成功。
  3. `({…})[name]` 這種字面量查表：撈到原型上的函式。
- 拿 `__proto__`、`constructor`、`toString` 各打一次。
- 保留字要拒收還是容忍、用什麼錯誤碼，是產品決定，專案寫明。
- 但拒收要明確報錯，不可以靜默丟掉。靜默的結果就是上面那種：改名變刪除，畫面還說成功。
- 考題裡含 `__proto__` 鍵的輸入，用 `JSON.parse` 或計算鍵 `{ ['__proto__']: … }` 造。不要寫 `{ '__proto__': … }` 或 `{ __proto__: … }`：那是設原型的語法，不會變成自有鍵（本機實測）。
- 要送出去的請求本文，直接寫成 JSON 字串。用 `JSON.stringify({ '__proto__': …, a: 1 })` 造，送出前鍵就沒了，只剩 `{"a":1}`（本機實測）。
- 新考題照規矩 E8。

### 考題守不到

- 瀏覽器端模組在 Node 裡載不進來時，前端那幾處沒有考題，只靠讀碼。
- 原專案 #150、#156 的說明寫明前端的修正是這樣守的。#150 那三種寫法都在前端。

## 4. 漏了 await、非同步的處理函式丟錯

### 適用條件

- JavaScript 的 async／Promise 程式。把原本同步的函式改成非同步時，特別要看。
- 「處理函式丟錯」那幾點，另外要：伺服器框架不接非同步處理函式丟的錯（例如 Express 4），路由處理函式或中介層又寫成 async。

### 會怎樣

- 漏了 await 不一定報錯。原專案 #303 的說明寫的是 `res.json(service())` 那種：不報錯，默默回 `{}`。本機實測：
  - Promise 直接轉 JSON 是 `{}`，包在物件裡也一樣。
  - 拿它當條件（if、!、&&）：Promise 一定是真值。`if (!isAllowed())` 永遠不會擋下。
  - 預設參數呼叫它：拿到 Promise，拿去乘是 NaN。
  - try 包著沒等的 `return work()`：finally 提早跑，catch 接不到錯。
  - 同步的呼叫端用 try／catch 包著，也接不到，最後變成沒人接的 rejection。
  - 讀它再下一層的屬性（`r.items.length`），才丟 TypeError。
- 沒等的寫入，呼叫端不等它就回了成功。它後來失敗時，那個成功已經送出去了（本機實測）。
- 沒有全域攔截時，那筆寫入後來失敗，整個伺服器行程結束，退出碼 1（本機實測）。
- 處理函式或中介層沒包、丟了錯（本機實測）：
  - 沒有全域攔截時，整個伺服器行程結束，退出碼 1。
  - 掛了 unhandledRejection 或 uncaughtException 攔截時，行程不死。但那個請求一直沒有回應（探針等了 1.5 秒都沒有回應），其他請求照常。
  - Express 5 起框架自己會接。這是外部文件說的，沒量過。

### 怎麼查

- 每個非同步呼叫都有等。函式從同步改成非同步時，另查這幾處不報錯的：
  - 預設參數呼叫它。
  - try 包著它卻沒等（catch 接不到、finally 提早跑）。
  - 同步的呼叫端直接用它的回傳值。
  - 拿它當條件（if、!、&&）。
- 只靠 TypeScript 的型別檢查（5.9.3，本機實測；量了 strict 開與關兩種）：
  - 抓得到：讀它的屬性、拿它算術、預設參數或回傳值的型別不合（strict 開或關都抓得到）。
  - 要開 strictNullChecks（strict 含它）才抓得到：拿它當 if 條件、&&、三元。沒開就不報。開了也有漏：while 的條件不報；先存成變數、if 區塊裡又用到那個變數，也不報。
  - 抓不到：`!promise`、交給收 any 的參數（例如 `res.json({ data: promise })`）、`JSON.stringify`、沒等的呼叫（`save();`）、try 裡沒等的 return、樣板字串。
- 看得懂型別的程式檢查規則，抓不抓得到沒等的寫入，沒量過。
- 每個 async 處理函式、中介層都包一層，把錯交給框架的錯誤處理（例如 Express 的 `next(err)`）。
- 包裝器只接得到有等的錯。沒等的寫入失敗，它接不到，行程照樣結束（本機實測）。
- 包裝器不只一種時，專案寫明各用在哪，不混用。原專案 #303 的說明寫：兩種包裝器回錯誤的樣子不同，換用就改了行為。

### 考題守不到

- 沒等的寫入，失敗發生在回應送出之後。只看回應的考題看不到它（本機實測：先回 200 `{"saved":true}`，50 毫秒後寫入才失敗）。
- 回成 `{}` 的那種，只斷言狀態碼的考題照樣綠（本機實測：狀態碼 200，本文 `{"data":{}}`）。

### 出處

- 原專案 #303（2026-07-27）<https://github.com/teacherjung/personal-finance-webapp/pull/303>：改成非同步時，十餘條回應要補 await；另修了 finally 提早跑、預設參數拿到 Promise 兩個陷阱；加了處理函式的包裝器。
- 標「本機實測」的後果，是本表的探針量的。

## 5. 讀出→改→寫回之間被別的請求插隊

### 適用條件

- JavaScript 伺服器以「讀出整份或一大塊→在記憶體改→寫回」存資料。
- 而且同一份資料會被幾個請求或背景工作改。
- 「插隊」那幾點，另外要：讀出與寫回本身不必等網路，例如底下是同步的本機資料庫。
- 資料庫要經網路非同步存取時，讀、寫本身就是等待，「插隊」那幾點的查法做不到。改看「重跑」「重抓版本」，或用交易、鎖。
- 「重跑」「重抓版本」那幾點，另外要：寫入時有版本比對（版本不合就不寫）。

### 會怎樣

- 插隊：讀和寫之間等了外部的事（網路、檔案、計時器），別的請求就可能插進來。寫回時把它的改動整個蓋掉，不報錯。
- 插隊，就算沒等外部（本機實測，把同步的儲存包成 async 讀寫）：
  - 兩條流程從不同的請求各自開始：2 筆都在。
  - 兩條流程一起等同一個 Promise，之後再讀改寫：只剩 1 筆。
  - 同一個請求裡用 Promise.all 跑兩條讀改寫：只剩 1 筆。
  - 兩個請求各自先等同一個「進行中就共用」的外部查詢，再讀改寫：兩個都回 200，只留下一筆。這正是照「外部資料先拿完再讀」做的。
  - 讀到寫之間完全不 await：2 筆都在。
- 重跑：衝突就整段重跑的寫入，重跑那段帶著外部副作用時，副作用會發生不只一次（推論的；原專案只有預防的考題，沒有事故）。
- 重抓版本：預期版本在寫入前一刻才重抓，等於自己蓋章給自己看，只保護「重抓到寫入」那一瞬間。原專案 #336 的說明寫：兩個分頁就重現。一頁還原備份時，另一頁存了新值；新值被舊值蓋掉，畫面回成功。

### 怎麼查

- 插隊：讀到寫之間，逐個 await 看它在等什麼。
  - 外部資料先拿完再讀；只改自己負責的欄位。
  - 讀到寫之間最好完全不 await。就算等的只是包成 async 的同步儲存，一起被叫醒的兩條流程（一起等同一個 Promise、用 Promise.all）還是會交錯，後寫的蓋掉先寫的（本機實測）。
  - 同一個請求的兩條寫入不並行，一條一條等。本機實測會丟一筆；原專案沒有事故。
- 重跑：重跑那段只算資料，不做別的事。對新讀出來的資料重跑也對，不放外部副作用（扣額度、發請求、寫別處）。考題讓它真的被重跑一次，斷言副作用只發生一次。這一條是推論的預防。
- 重抓版本：預期版本要來自讀出這份資料的那一次讀取。
  - 改動在呼叫端記憶體裡、資料層重算不了的整包寫入，撞版本就回衝突（例如 HTTP 409）。
  - 不拿舊快照重試：那等於把別人剛寫的吃掉。

並發考題（插隊、重抓版本）：

- 讓兩個請求真的交錯。判準分兩種：能重算、兩邊都該成功的（插隊），斷言兩邊的改動都還在；資料層重算不了的整包寫入（重抓版本），斷言版本過期的那一邊回衝突、沒有寫進去，成功的那一邊資料保留（原專案 #336 的考題就是這樣斷言）。
- 交錯點做成一定停在那裡、只停一次的開關，不靠碰運氣的時序（原專案 #336 的做法）。
- 再補一題「沒有人插隊時照常成功」，免得為了過考題把整條路擋死（原專案 #336）。

### 考題守不到

- 並發考題只守它打的那幾條路。別條路的讀寫之間新夾一個外部等待，照樣綠（推論的；出處有讀考題的佐證）。
- 兩個請求各自開始的考題，抓不到「一起被叫醒」那一種交錯（本機實測：各自開始時 2 筆都在）。
- 並發考題跑在哪一種儲存上，就只證明那一種。「插隊」的前提換成網路資料庫時，原本的考題可能照樣綠（推論的）。

### 出處

- 插隊：原專案 #132（2026-07-19）<https://github.com/teacherjung/personal-finance-webapp/pull/132>。同步外部資料期間寫入的資料，同步完成後整個消失（說明寫是實測的）。修法是外部回來之後才讀整包。
- 插隊：原專案 #186（2026-07-21）<https://github.com/teacherjung/personal-finance-webapp/pull/186>，同型第二次：抓報價期間的記帳被無聲吞掉。修法是回來後重讀，只合併自己負責的欄位。
- 插隊的前提：原專案 #309（2026-07-28）<https://github.com/teacherjung/personal-finance-webapp/pull/309>。讀寫之間夾了一次讀取，本機的同步資料庫看不出來；換成網路資料庫就打開交錯的窗口。
- 插隊考題的射程：2026-10-06 讀原專案主幹，為「讀寫之間不夾外部等待」寫的那組並發考題，兩題都只打同一條路（沒做突變）。
- 重跑：同上 #309，版本不合時重讀、重做、重寫一次。原專案 #515（2026-08-26）<https://github.com/teacherjung/personal-finance-webapp/pull/515> 加了「重跑兩次仍只算一次」的考題（預防，沒有事故）。
- 重抓版本：同上 #309，資料層重算不了的整包寫入回 409，不假裝重試。
- 重抓版本：原專案 #336（2026-07-29）<https://github.com/teacherjung/personal-finance-webapp/pull/336>。說明寫：上線前最後一輪檢查抓到，**實作者** 自己重現確認。

## 6. 讀不出來的欄位，被回退值蓋掉

### 適用條件

- 程式整份讀出、改一處、再整份寫回。同步、非同步都算。
- 而且讀不出來的欄位（例如解密失敗、格式壞掉）會回退成空值或預設值。

### 會怎樣

- 回退的空值，在下一次整份寫回時把原值蓋掉。之後讀對了，也救不回來。
- 原專案 #329 的說明寫：金鑰設錯一次、新增一筆無關的資料，密文就被空字串蓋掉。換回正確金鑰也救不回來。

### 怎麼查

- 讀不出來的欄位記下原值，寫回時沿用原值，不寫回退的值。
- 記下的原值只用在同一個請求、同一次讀取。跨請求共用，可能寫進別的使用者的資料；重試前沒清掉，可能把另一個請求剛清空的值復活（原專案 #329 的說明）。
- 按路徑記原值時，兩筆算出同一條路徑的不記。寧可少救一個欄位，也不要把甲的值寫到乙（原專案 #329 的說明）。
- 查法：讓一個欄位讀不出來，做一次無關的寫入，再讓它讀得出來。原值要還在。

### 考題守不到

- 只測「讀不出來時不崩潰、回空值」的考題，照樣綠。壞的是下一次寫入（推論的）。

### 出處

- 原專案 #329（2026-07-28）<https://github.com/teacherjung/personal-finance-webapp/pull/329>：上線前抓到。說明附了重現步驟；三處保護各做過一次突變。

## 7. 程式存著機密或個資時的每一種回應

### 適用條件

- 程式在後端存著「機密」或個資（密碼、權杖、證件號碼、完整帳號這類）。
- 個資那一半是推論的延伸：出處兩支講的都是密碼與權杖。
- 而且有回應會把資料送出去：給畫面，或給別的程式。
- 這一節的射程是回應。錯誤訊息、日誌沒有出處，沒寫進來。
- 匯出檔要不要帶機密，是產品決定，專案寫明。

### 會怎樣

- 只在「讀取」那條路遮住時，新增、修改的回應照樣把值送回去。
- 原專案 #168 的說明寫：新增或修改卡片、設定，回應把密碼與權杖送回瀏覽器，改個匯率都會。

### 怎麼查

- 讀取、新增、修改的每一種回應，都只給「有沒有設定」或遮過的片段（例如末四碼），不給完整值或密文。
- 先用隔離資料（規矩 B4）種一串認得出來的假值，確認程式真的收到（例如「有沒有設定」回 true）。
- 種的值只用英數字。含 `"` 或 `\` 的值，在 JSON 回應裡找不到原字（本機實測）。
- 再到每一種回應的全文裡，找那一串值。也找資料庫存的那串密文。
- 不只比形狀：形狀比對會被欄位改名繞過（原專案 #340 的說明）。值比對不怕改名，但值被編碼、拆段、轉義過就比不到。本機實測：明文變成密文或 base64，搜明文就找不到；拆段沒量過。
- 值遮住以後，表單顯示不了原值。留空代表什麼、怎麼清除，是產品決定，專案寫明。
- 要確認清得掉（原專案 #168 修之前只能改、不能清）。

### 考題守不到

- 沒先種機密的考題，「遮掉了」和「本來就沒有」長得一樣。原專案 #340 的說明寫：這樣的探針，把遮蔽整層拆掉照樣綠。
- 每一種回應各要一題。只有讀取那一題時，新增、修改的回應漏了照樣綠（推論的）。

### 出處

- 原專案 #168（2026-07-20）<https://github.com/teacherjung/personal-finance-webapp/pull/168>：遮蔽只掛在讀取。同一支補了寫入端的遮蔽，也加了「清除已設定」（修之前只能改、不能清）。
- 原專案 #340（2026-07-29）<https://github.com/teacherjung/personal-finance-webapp/pull/340>：探針沒種機密、只比形狀。改成先經正式的介面種三個機密、確認收到，再找那幾串值。

## 8. 畫面上講資料或機密去向的字

### 適用條件

- 程式在畫面上告訴使用者資料或「機密」會去哪：含不含機密、會不會上傳、存不存。
- 而且答案會隨執行環境或設定改變（例如本機版和雲端版），程式要問了才知道。

### 會怎樣

- 寫死一句，到另一個環境就可能說反。原專案 #438 的說明寫：上傳密碼的欄位寫「不會上傳」，在雲端版那正是在上傳。
- 兩個環境刻意給不同的東西，畫面卻兩邊都講「不含機密」。在含機密的那個環境，讀到的人會把檔案當成不敏感的，轉寄出去（原專案 #417 合併提交說明的推論）。
- JavaScript：原型鏈上的值，也能騙出放心的那一句（原專案 #441，見第 3 節）。只在原型鏈上的 true，`=== true` 照樣成立（本機實測）。
- 原專案 #417 的合併提交說明寫：「講錯方向比不講更糟」。

### 怎麼查

- 先照「複審必驗清單」裡「新增或改了畫面上的狀態、說明文字時」那一項。這一節只補「答不出來時往哪邊錯」。
- 只有程式明確答出來，才講讓人放心的那一句。明確＝嚴格比對答案本身（JavaScript：還要是自有欄位，例如 `Object.hasOwn(x, 'k') && x.k === true`）。
- 答不出來（逾時、連不上、回應形狀不對、型別不對）時，講保守的那一句。方向同規矩 E5「查不到就擋下」。
- 哪一句算保守，看它在保護什麼。原專案兩處方向相反：匯出前的告知，問不到就講「含機密」；上傳密碼的欄位，問不到就講「會上傳」。
- 去問答案的那一步要有時間上限，不讓畫面卡住（原專案 #438 設了 5 秒）。
- 那一項要找的輸入，這一類至少含：逾時、錯誤、字串 `'true'`；JavaScript 另加只在原型鏈上的值。

### 考題守不到

- 挑句子的考題只證明「挑哪一句」。畫面有沒有真的用它，要另一題守接線。
- 另一個環境的那一句，要在那個環境真的跑起來才看得到。原專案 #438 的說明寫：雲端那一句只用考題鎖住，沒起雲端環境實測。

### 出處

- 原專案 #417（2026-08-08）<https://github.com/teacherjung/personal-finance-webapp/pull/417>：「複審」第 4 輪擋下「兩種環境都寫不含機密」；改成依環境分流，問不到就講「含機密」。這段寫在合併提交的說明裡（**實作者** 當時的紀錄），PR 說明沒寫。
- 原專案 #438（2026-08-11）<https://github.com/teacherjung/personal-finance-webapp/pull/438>：上傳密碼欄說反。保守的方向跟匯出告知刻意相反。加了挑句考題，另一題守接線。
- 原專案 #441（2026-08-11）<https://github.com/teacherjung/personal-finance-webapp/pull/441>：#438 的「複審」抓到同型：原型鏈上的值騙出「不含機密」那一句。修法是先認自有欄位，再嚴格比對。
