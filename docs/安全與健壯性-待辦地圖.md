# 安全與健壯性 — 待辦地圖（邁向多人服務）

> 這是一次自我體檢的結果，對照「終點＝多人註冊使用的服務」。
> **目前 app 只綁 `127.0.0.1`（只有你自己的電腦連得到）、單人使用，以下多為「開放給別人用之前必須做」的項目**，現在不是 bug。
> 每項標了該在哪個階段做（A 安全網✅／B 骨架改建／C 多人前置）與白話說明。

## 🟢 已完成（階段 A 安全網）
- 自動考試（`npm test`，34 題）、型別校對（`npm run typecheck`）、格式糾察（`npm run lint`）、兩道自動守門（pre-push＋CI）。
- 資料防呆第一塊：`store.json` 讀取失敗 fail closed（不再默默回空庫覆蓋資料，PR #53）。

---

## 🔴 高優先（開放多人前「必須」，階段 B/C）

### B1. 併發寫入會互相覆蓋 → 換 SQLite
- **白話**：現在全部資料在一個文字檔。兩個人（或同一人兩個分頁）同時存檔，後存的會蓋掉先存的，資料遺失。
- **現況**：`lib/store.js save()` 是「整包讀出→改→整包寫回」，無鎖。
- **做法**：階段 B 換成 SQLite（單檔、免架伺服器，但支援交易與併發）；資料存取先收斂到單一 repository 櫃檯，換引擎時其他程式不用動。

### C1. 沒有帳號與資料隔離
- **白話**：現在誰連得到就看得到全部資料。多人服務必須「登入後只看自己的帳」。
- **做法**：階段 C 加帳號系統（註冊/登入/密碼**雜湊**存放，絕不存明文）；每筆資料綁 userId，所有查詢都過濾 userId。

### C2. 敏感資料明文儲存／外流風險
- **白話**：帳單 PDF 密碼（＝身分證字號）、IB Flex Token 目前明文存在 `store.json`。單機沒差；上了伺服器，一旦被讀到就是重大外洩。
- **現況**：`GET /api/db` 回**整包**（含 `settings.ib.flexToken`）；`GET /api/settings` 也回 token。
- **做法**：階段 C——敏感欄位加密存放（或改用只在本機、不上傳的設計）；API 回傳前遮蔽 token；`/api/db` 這種「整包匯出」端點要加權限。

### C3. 傳輸未加密（HTTP）
- **白話**：多人服務要用 HTTPS（加密連線），否則帳密與財務資料在網路上是明文。
- **做法**：階段 C 上線時用反向代理（如 Caddy／Nginx）自動 HTTPS。

## 🟠 中優先（階段 B 一併做，健壯性）

### B2. API 全盤接受前端傳來的欄位（無白名單）
- **白話**：新增/修改資料時，後端把前端送來的內容**照單全收**。單人可信；多人時，惡意或寫錯的前端可塞任意欄位（例如偽造 `source:'ib'`、蓋掉計算欄位）。
- **現況**：`server.js` CRUD 用 `{ ...req.body }`／`{ ...list[i], ...req.body }`。
- **做法**：階段 B 把資料存取收進 repository 時，順便對每個集合做「只接受這些欄位」的白名單。

### B3. 缺乏輸入驗證與大小/數量上限
- **白話**：金額、日期、字串長度、陣列筆數都沒設限。多人時可能被灌爆或塞入怪資料。
- **做法**：階段 B 在 repository/端點層加基本驗證（型別、範圍、長度）。

### B4. 錯誤處理不一致
- **白話**：部分端點沒有 try/catch，壞資料可能讓整個伺服器回 500 甚至不穩。
- **做法**：階段 B 分層時加統一的錯誤處理中介。

---

## 🟡 低優先（有空再做）
- **B5. 速率限制／濫用防護**：多人服務要防有人狂打 API（階段 C 上線前）。
- **B6. 稽核日誌**：誰在什麼時候改了什麼，出事好追（多人時有用）。
- **B7. 備份自動化**：目前靠手動「匯出備份」；多人時要自動定期備份。

## 給 Codex／維護者
以上多為**架構性、分階段處理**的項目，**不是現在要當 bug 修的**——請勿在單人版對這些「開洞」（例如不要為了「安全」把只在本機用的功能改壞）。正確性 bug 照抓。此地圖隨階段推進更新。
