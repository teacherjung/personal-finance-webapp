# 銀行收支單筆刪除後的讀取恢復

## 定案與範圍

接續原工程第4／6項未涵蓋的銀行收支單筆刪除，產品基底為 `c4a080609a7a82df4365d41526d7916d40f8cb89`。本人分別答「採用這版，接續施工（建議）」及「提示與同列防重操作一起採用（建議）」，[E10完整留痕](https://github.com/teacherjung/personal-finance-webapp/pull/704#issuecomment-6247125503)只核本次提示／操作，不是合併後H6。技術依[實際GPT‑6.1 Sol／xhigh完整裁示](https://github.com/teacherjung/personal-finance-webapp/pull/704#issuecomment-6247040421)，不是本人技術原話，也不是正式複審放行。

收到正式刪除成功回應後，有本次成功列表就保留原列表、摘要與篩選，標題下、列表上方說明「資料已刪除，畫面尚未更新」；無可用列表則說明「資料已刪除，暫時無法載入列表」。按「重新讀取」只讀既有端點，不再DELETE。成功且讀取開始時已涵蓋確認修訂才清除提示；失敗或未知回音不猜已刪或必定未刪。

同 id 在途或已確認刪除而舊列仍在時不重送DELETE；其他 id 可獨立操作，不設全頁寫入鎖。原生確認逐字沿原來源模板、金流及 `money()`；取消零請求。無新刪除回焦目的地，既有編輯阻擋文案及重讀回焦保持。

## 技術界線

模組私有單筆續行分開確認、修訂與讀取，不改共用 `confirmDelete`、router、樣式、後端或資料格式。正常API回應的 `ok === true` 才取得確認資格；先登記 `editRevision`、刪除修訂及同id確認紀錄，再核原工作區、原列／鈕、visit／host／完整hash／nav／route／generation、最新已接受刪除、在途讀取及 `watchModalRoot()`。取消不淘汰其他已接受作業；較晚舊確認仍登記事實，但不在新頁／新窗報舊成功或多起GET。

不完整欄位回音優先於未涵蓋刪除，後者優先於既有匯入／普通儲存文字；後續寫入不抹刪除事實。有效完整讀取按開始修訂清提示及已涵蓋同id紀錄，舊控制項另以實體工作區身分拒絕。確認使舊編輯表單沿原規則失效，但不改欄位、不關窗或升級其修訂。確認後GET的失敗不撤回確認、不重送DELETE，也不走DELETE失敗處理。

## 回歸與證據射程

外置未修版探針使用正式app／cashflow圖與本題專屬資料，先證DELETE真正移除資料且次數，再對有／無列表的刪除待更新提示得到預期assertion紅。補充反例量到同id重送、晚確認重畫其他頁與新窗後多起GET；取消及負回應屬既有可保存行為。初版補充探針的確認句預期漏原金額單位，已從實測原句修正；該題的首次紅不是產品缺陷，原日誌保留。

正式行為題沿既有 `test/cashflow-reload.test.js`，保留原重讀／匯入／回焦斷言，擴充嚴格成功、失敗、取消、未知回音、同id鎖與已刪紀錄、不同id交錯、讀取開始修訂、五端點失敗、換頁／返回／新窗、舊表單、優先序及空列表。fixture只用合成fetch／DOM；不把它稱為原生確認框或真正後端證明。

突變在樹外：先核替換目標唯一及正常基線綠，再移除修訂、同id在途／確認保護、原入口、最新作業、讀取世代、彈窗世代、嚴格回音、讀取開始清理、提示優先、確認返回重核、在途讀取、鎖收尾及id不唯一保護。各組保留受測DELETE／GET，對應考題均出現assertion紅；不以語法、import或fixture錯誤充數。逐輪題數、雜湊與原始輸出留私有證據及本支PR，不在本檔預寫後續閘結果。

原生驗證使用獨立新建外置 `STORE_FILE`、合成交易、停用外部來源，產品JavaScript原樣提供；僅fixture控制回應失敗與延後。已實走原生確認取消／接受、同列防重、有列表失敗／GET-only恢復、晚確認離頁返回無列表提示與空列表恢復，以及既有重試失敗／成功回焦。原生交錯、全部正式路由重載與console觀測分別留證；跨瀏覽器及全部UI7未宣稱完成。靜態候選、真DOM與正式後端／原生證據分開。
