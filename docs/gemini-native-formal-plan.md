## 本階段的目的與界線

原生候選版已在私人合成試跑中產生可採用的結構化答案，但該試跑使用的認證例外不是正式掃描授權。依本次 GPT‑6.1 Sol 技術裁示，本支先完成不含真認證的程式準備；正式入口拒絕執行，不修改 scanner 設定，不啟動官方原生 CLI。此文件記錄工程安排，不代表 William 已核定任何新例外。

原有 API relay 路徑、既有掃描紀錄及舊失敗收據保留。本支不追認任何先前試跑為 G1 掃描，也不補掃已獲個案免掃的工作。

## 施工順序

1. 在本次獨立施工樹實作；原常設樹已有別線工作，不切換、不整理其改動。只修改專案自有檔案，開工與送審均查共用檔清單。
2. 建立完整單筆 UTF‑8 NDJSON 輸入及封閉 findings schema。候選答案只取 `structured_output`；一般 response 不當備援答案。驗證對話、單回合、事件生命週期、唯一末尾 finish、模型與材料綁定。每場在全部材料之後加入新的 256-bit 隨機挑戰；預期值不放在前置 binding 或 schema，空 findings 也須精確回覆。
3. 建立材料與來源核對的準備入口，正式入口在讀取認證或啟動子程序之前拒絕。材料限已提交的 base／head 差異與前後檔案；拒絕敏感路徑、二進位及不完整材料。
4. 用合成子程序驗證背壓、EOF、提前關閉、逾時、中斷、輸出限額與程序群收尾。考題不讀取真實憑證、不呼叫官方 CLI、不外連；來源變動與拒絕閘另做有效突變。
5. 跑專案檢查與獨立複審；本支保留草稿直到所需裁示及程序完成。

傳輸收據的寫入完成，只表示位元組已交給底層系統，不證明接收端已完整消耗。尾端挑戰只支持回覆端取得該場尾端值，不能證明官方 CLI 或模型逐位元組讀完、保留或理解中段材料；惡意程序仍可能讀到尾端而忽略中段。協議收據分列結構驗證、尾端挑戰比對與未證實的接收端消耗，只回傳候選答案，正式入口仍拒絕啟動。[本輪技術答覆與待辦安排](https://github.com/teacherjung/personal-finance-webapp/pull/693#issuecomment-6220998504)。

## 限額與預期檔案

- 材料上限 4 MiB，超量拒收，不截斷；傳輸上限包含 JSON 跳脫的最壞放大。
- 候選原生內部時限 120 秒、外層 150 秒；stdout 與 stderr 合計 256 KiB，一般 response 上限 64 KiB。這些是待接線上限，不是大變更一定能在限內完成的保證。
- 程式：`scripts/gemini-native-protocol.js`、`scripts/gemini-native-transport.js`、`scripts/gemini-native-runner.js`。
- 考題：對應的 `test/gemini-native-*.test.js` 與 `test/helpers/gemini-native-fixture.js`。
- 說明：本文件及 `docs/project-collaboration.md`。不更動套件檔、禁區清單、全域鉤子或帳號設定。
