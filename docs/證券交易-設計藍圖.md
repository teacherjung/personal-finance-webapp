# 證券交易分頁設計藍圖

> 狀態：**只完成設計，尚未動工**
>
> 目的：建立一個專門查閱與核對買賣紀錄的分頁。它和「投資組合」分工明確：投資組合負責分析與呈現目前部位；證券交易負責忠實保存、搜尋與核對過去成交。

## 一、使用者真正要解決的問題

使用者需要在同一個地方查兩種券商來源：

1. IBKR Flex Query 同步的成交紀錄。
2. 使用者上傳的台新證券電子對帳單。

這個分頁主要回答：

- 我在什麼時候買了或賣了什麼？
- 成交股數、成交價、手續費、稅與實際應收付是多少？
- 這筆資料來自哪一家券商、哪次同步或哪份對帳單？
- 同一段期間有沒有重複匯入、漏匯或讀不懂的資料？

這個分頁**不負責**回答：

- 現在的持股配置是否合理。
- 股票、債券、黃金各占多少。
- 區域、幣別、公司曝險與投資紀律。
- 未實現損益、淨值走勢或資金加權年化報酬。

上述分析仍留在「投資組合」頁，避免查帳頁同時塞進太多圖表與投資判斷。

## 二、頁面位置與第一版排版

### 導覽位置

建議放在「投資組合」正下方：

1. 投資組合
2. 證券交易
3. 訂閱追蹤

這樣「投資組合」是目前狀態與分析，「證券交易」是歷史流水與對帳，兩者靠近但不混在一起。

### 頁首

- 標題：`證券交易`
- 說明：`集中查閱 IBKR 與台新證券的買賣紀錄，方便搜尋與對帳。`
- 主要按鈕：
  - `同步 IBKR`
  - `上傳台新證券對帳單`
- 次要按鈕：`匯入紀錄`

兩個主要按鈕應使用相同高度與寬度。同步 IBKR 必須呼叫既有的同一套同步服務，不能在新頁另寫一套。

### 第一列：期間摘要

摘要只協助查帳，不做績效分析：

- 成交筆數
- 買進總額
- 賣出總額
- 手續費與稅
- 淨應收付

每張摘要都只計算目前篩選期間與幣別。不同幣別不可默默加總；預設分幣別顯示，除非有明確匯率來源與註解。

### 第二列：查詢工具列

- 日期範圍：本月、近三月、今年、自訂
- 券商來源：全部、IBKR、台新證券
- 帳戶：以遮罩名稱顯示
- 買賣方向：全部、買進、賣出
- 市場或幣別
- 搜尋：證券代號或名稱
- 排序：所有表格欄位都可獨立排序

### 主表格

第一版建議欄位：

| 欄位 | 說明 |
|---|---|
| 成交日 | 本地日曆日，不用 UTC 直接解析 |
| 交割日 | 台新對帳單有資料才顯示；IBKR 無資料可留空 |
| 來源 | IBKR 或台新證券 |
| 帳戶 | 只顯示遮罩名稱，不送完整帳號到前端 |
| 證券 | 代號為主、名稱為輔 |
| 買賣 | 買進或賣出 |
| 數量 | 保留來源所需小數位 |
| 成交價 | 顯示原幣 |
| 成交金額 | 來源原始成交金額 |
| 手續費與稅 | 表格可合計，展開後列細項 |
| 淨應收付 | 以買進流出、賣出流入的方向顯示 |
| 幣別 | TWD、USD、GBP、JPY 等 |

每列可展開，查看來源保留的明細，例如折讓、證交稅、融資欄位、來源批次、原始交易識別碼。主表維持安靜，細節需要時才展開。

### 空狀態

`尚無證券交易。可同步 IBKR，或上傳台新證券對帳單。`

## 三、台新證券 PDF 的實際結構

本藍圖已用使用者提供的兩頁 A4 加密對帳單做本機版面校準，**沒有把姓名、帳號、密碼或真實交易寫入本文件**。

### 第一頁：資產概況

可辨識：

- 對帳單年月
- 券商名稱
- 各類資產市值
- 資產總淨額
- 資產配置比例

第一版建議只把「對帳單年月」當匯入批次資訊。資產概況先不寫進投資組合，也不自動覆蓋持股，原因是：

- 一份月結資產概況不等於完整交易歷史。
- 股票分割、移轉、配股、借券與對帳單未涵蓋的舊交易，都可能讓用成交回推持股失真。
- 投資組合目前有自己的持股與 IBKR 同步規則，直接覆蓋會造成同步點與資料所有權衝突。

未來可新增「持股對帳」功能，只提示差異、由使用者確認，不能靜默改寫投資組合。

### 第二頁：成交明細

實際版面有以下特性：

- 雙層表頭，同一個欄位位置上下代表不同名稱。
- 一筆成交跨兩行：第一行是成交日、代號、數量、價格等；第二行是交易類別、證券名稱、成交金額與費稅等。
- 多筆成交後另有交割彙總列，提供應收付日期與合計金額。
- 同一交割日可能對應多筆成交。
- 頁尾有大量法規說明文字，解析器必須在交易表結束後停止，不能把法規數字誤當成交。

因此不能沿用信用卡帳單解析器，也不能只按文字順序切行。解析器必須保留文字的 x、y 座標，依欄位位置與相鄰行距組合交易。

### 初版要辨識的台新欄位

- 對帳單年月
- 帳戶識別資訊，只保留遮罩顯示與不可逆指紋
- 成交日
- 交割日
- 交易類別，例如現買、現賣
- 證券代號
- 證券名稱
- 數量
- 成交價
- 成交金額
- 手續費
- 折讓金額
- 證交稅
- 其他費用欄位
- 應收付金額
- 幣別，這份格式預設為 TWD，但解析器不可假裝所有格式都一定是 TWD

對帳單印出的「應收付金額」是查帳真相。程式可以用成交金額與費稅做交叉檢查，但不可因自己推導不同就偷偷改掉來源數字；應在預覽中標示「金額無法核對」並阻擋確認。

## 四、共同交易格式

建議新增獨立集合 `securityTrades`，不要把台新資料塞進現有 `ibTrades`。

```text
id
source                 ibkr | taishin
sourceAccountId        內部穩定帳戶身分
sourceAccountLabel     前端可見的遮罩名稱
tradeDate              YYYY-MM-DD
settlementDate         YYYY-MM-DD，可空
symbol
name
side                   buy | sell
quantity
price
grossAmount
commission
tax
feeDiscount
otherFees
netSettlement          來源顯示的應收付絕對值
cashDirection          in | out
currency
market
sourceRef              來源去重鍵，服務層擁有
importBatch            匯入或同步批次
importedAt
rawType                 來源原始交易類別，供查錯
```

所有金額保留原幣。買賣方向與現金方向分開保存：買進通常是 `cashDirection:'out'`，賣出通常是 `cashDirection:'in'`。不靠金額正負猜方向。

`sourceRef`、`importBatch`、`importedAt` 與來源帳戶身分都是服務層欄位：

- 進 `FIELD_SCHEMA` 與型別定義。
- 不進一般 CRUD 白名單。
- 匯入備份必須保留。
- GET 回應必須經機密投影。

## 五、IBKR 與台新的資料流

### IBKR

```text
Flex Query
  -> 既有 lib/ib.js 解析
  -> 共用證券交易正規化器
  -> securityTrades 依來源識別碼 upsert
  -> 證券交易頁查閱
```

既有 `ibTrades` 仍被投資組合的交易摘要與 XIRR 使用。第一階段不要直接移除：

1. `syncIb` 在同一次資料庫寫入中，同步更新既有 `ibTrades` 與新的 `securityTrades`。
2. 補一題同步考試，保證兩邊的 IBKR 成交筆數與核心金額一致。
3. 等證券交易頁穩定後，再用另一支 money-critical PR 讓投資組合改讀共同集合。
4. 最後才評估移除 `ibTrades` 相容鏡像。

IBKR 應優先使用 Execution ID、Transaction ID 或其他官方穩定識別碼。若目前 Flex Query 沒勾，施工時要先確認可用欄位；不得只靠日期與代號去重，因為同日同價可以合法成交多筆。

同步採「重疊期間 upsert」，不能因新報表沒出現舊交易就刪除歷史。這可避免 Flex Query 期間變短時，查帳紀錄突然消失。

### 台新證券

```text
加密 PDF + 本次輸入的密碼
  -> 只在記憶體解密
  -> 台新專用座標解析器
  -> 預覽與對帳檢查
  -> 使用者確認
  -> securityTrades upsert
```

密碼預設每次上傳時輸入，不寫入資料庫、不送回瀏覽器、不進 log。未來若使用者明確要求「記住密碼」，必須沿用機密投影與可清除設計，且在多人化前重新評估加密存放。

## 六、去重與資料安全

### IBKR 去重

優先順序：

1. 官方 Execution ID 或 Transaction ID。
2. 帳戶身分 + 官方訂單／成交識別碼。
3. 只在來源缺識別碼時，才使用日期、代號、買賣、數量、價格、淨現金與同批出現序組成退路指紋。

### 台新去重

建議鍵：

`券商 + 帳戶指紋 + 成交日 + 代號 + 類別 + 數量 + 成交價 + 成交金額 + 應收付金額`（**S2 修訂：移除「對帳單年月」**——同筆交易跨月重印會變兩鍵、違反下方「重疊月份不可重複入帳」；**「同批出現序」不再作為跨批身分**，改由匯入端的「內容比對＋計數對帳」處理同鍵多筆，序號只在插入時取「庫內既有最大＋1」）

同日、同代號、同數量、同價格的兩筆交易可以同時存在，所以同批出現序不可省略。重匯同一份 PDF 必須得到 0 筆新增；上傳涵蓋重疊月份的另一份對帳單，也不可重複入帳。

### 帳戶與密碼

- 完整券商帳號不送前端。
- 文件中不保存真帳號、真末碼與密碼。
- 帳戶比對使用伺服器端的穩定指紋，畫面只顯示券商名與遮罩名稱。
- PDF 原檔不保存、不提交 Git。
- 錯誤訊息不可印出 PDF 密碼或完整帳號。

## 七、上傳預覽與阻擋規則

上傳後先顯示預覽：

- 對帳單年月
- 券商與遮罩帳戶
- 買進／賣出筆數
- 成交總額
- 手續費與稅
- 應收付合計
- 新增、重複、無法辨識各幾筆

下列情況 fail-closed，不讓使用者確認匯入：

- 密碼錯誤。
- 讀不到對帳單年月。
- 讀不到交易表頭或欄位位置。
- 交易類別不是已知枚舉。
- 日期不是真實日曆日。
- 數量、價格或核心金額不是有限數字。
- 單筆金額超過合理解析上限。
- 明細應收付加總與來源彙總明顯不符。
- 帳戶或幣別無法判定，且會造成跨帳戶／跨幣別誤併。

不認識的新交易類別要顯示原文與所在列，不能默默猜成買進或賣出。

## 八、匯入紀錄與後悔機制

`匯入紀錄` 彈窗列出：

- 來源
- 帳戶
- 期間
- 匯入時間
- 成交筆數
- 買進／賣出金額

台新 PDF 批次可整批刪除後重匯；刪除時必須同時比對 `source:'taishin'` 與批次 id，不能誤刪 IBKR 或其他批次。

IBKR 同步批次不提供一般「整批刪除」，避免誤刪長期歷史。若同步資料有問題，應重新同步同一期間覆寫相同來源識別碼，或進入專門的資料修復流程。

## 九、與投資組合的邊界

| 證券交易 | 投資組合 |
|---|---|
| 歷史成交與對帳 | 目前持股與配置 |
| 忠實呈現來源數字 | 匯率換算、曝險與報酬分析 |
| 搜尋、篩選、排序 | 圖表、紀律提醒、估值訊號 |
| 不自動推回持股 | 持股由 IBKR 同步或使用者維護 |
| 不判斷投資好壞 | 協助判斷配置與風險 |

第一版可以從交易代號連到投資組合的同一標的，但不能讓查帳頁直接修改持股。

## 十一、必考邊界

- 一筆成交跨兩行仍只產生一筆。
- 兩筆交易共用一個交割日，兩筆都得到正確交割日。
- 同日同代號同數量同價格的兩筆真交易都保留。
- 同一份 PDF 重匯不新增。
- 前一月交易出現在下一月對帳單時，年份與月份正確。
- 交易表跨頁時，頁尾法規數字不被當交易。
- 未知交易類別阻擋，不猜方向。
- 買進與賣出的現金方向正確。
- 不同幣別不直接相加。
- IBKR 同步期間縮短時，舊歷史不被刪。
- IBKR 同步等待網路期間的新寫入不被過期快照蓋掉。
- 完整帳號與密碼不出現在 GET、錯誤訊息、log、測試或 Git。
- 台新批次刪除不碰 IBKR。
- 新頁故障不影響投資組合正常顯示。

## 十二、目前建議的產品決定

1. 第一版只做查閱與對帳，不做績效圖表。
2. 第一頁資產概況先不覆蓋投資組合，未來只做差異提示。
3. PDF 密碼第一版每次輸入，不保存。
4. IBKR 與台新共用一張查詢表，但各自保留來源與原幣。
5. 台新應收付金額以對帳單為準，程式推導只用於核對與阻擋。
6. 新頁預設唯讀；日後若要加備註，備註應是獨立的使用者欄位，不改來源原始欄位。

1. **PDF 密碼＝存本機**（使用者拍板，推翻本文件產品決定 3）：`settings.taishinSecPdfPassword`，機密投影剝除＋`Set` 布林、備份保留、上傳時可臨時覆蓋。

3. **指紋類（無官方識別碼）跨批身分＝內容比對＋計數對帳**（`reconcileFingerprintRows`）：任何「批內出現序」都是批相對的——視窗位移會覆寫別筆、補印插入會漏記（自審兩條 HIGH、真碼重現）。指紋列入庫後不可變；只有官方識別碼列允許就地更新，且更新＝**整列取代資料欄**（防來源欄位消失後舊值殘留）。
4. **鏡像一致性語意＝「同步窗內 ibTrades ⊆ securityTrades」**而非相等（ibTrades 整包取代 vs securityTrades 永不刪，期間縮短後筆數必不等）。
5. **幣別牆擴及 securityTrades**（預覽 blocker／同步跳過＋回報）；核心金額（價/成交額/應收付）非有限數字＝blocker（§七 補強）。
6. 讀取單一入口＝`GET /api/securities`（通用 READONLY GET 迴圈明確跳過本集合）。

### §十三之二：Codex S2 複審 r1（2026-07-23，7 條全修）

1. **IB 缺幣別不猜 USD**（高）：Currency/Trade Price/Trade Money/Net Cash 都是 Flex 可個別勾選欄位——缺幣別或核心金額＝跳過＋分原因回報（前端指路補勾哪個欄位），絕不預設 USD。
2. **外層帳戶繼承＋誠實計數**：Trade 節點缺 Account ID 時繼承 statement 外層帳戶；跳過總數以**原始列數**為基準（壞列也算）、`secSkippedReasons` 分原因，前端同步訊息顯示警告。
3. **手續費幣別**：`commissionCurrency`（IB ibCommissionCurrency）——與交易幣別不同才存；不同幣別費用不可混單位（S3 顯示分開標）。
4. **官方識別碼鍵含帳戶指紋**（Claude 裁定採納：IB 未承諾 ID 跨帳戶唯一、§六優先序 2 本文即要求）：`ib|txn|<fp>|<id>`；舊格式鍵由同步時一次性冪等遷移（用列上自帶的 sourceAccountId 升級）。
5. **備份驗證牆＝完整合約**：必填擴為 tradeDate/sourceRef/source/symbol/side/quantity/cashDirection/currency——殘缺列擋在門口，不讓它穿過還原牆。
6. **securityTrades 機密投影**：`projectSecurityTrade` 剝 `sourceAccountId` 與 `sourceRef`（指紋非真不可逆、ref 嵌指紋），套 `GET /api/securities` 與 `/api/db`；`/api/export` 完整保留（還原冪等靠 sourceRef）。展開列的「原始交易識別碼」顯示需求由 S3 另行以安全投影變體處理。
7. **對帳單年月過真實日曆**：13 月/00 月直接 null → 400（防 MM/DD 年份推斷連鎖錯）。

### §十三之三：S3 合併後複審 r2＋「同步 IBKR」產品裁決（2026-07-24）

**產品裁決 A′（William 拍板）**——解決「查帳頁不改持股」與「同步 IBKR 會更新持股」的語意衝突：

- 保留**唯一一套完整同步**（`/api/ib/sync`），不另造「只寫成交紀錄」的第二套入口（兩套 IB 解析規則日後必然互相走偏）。
- 證券頁按鈕文案講明「與投資組合頁同一套完整同步：會一併更新持股與各幣別現金」；就地解釋（boundary）同步修訂。
- 「可能已出清」持股：證券頁**只提醒＋指路投資組合頁**（`missingHoldingsNotice`），**不做**確認刪除——「查帳頁不改持股」自此精確定義為「頁面上沒有任何編輯持股的功能」，同步服務本身更新持股不在此限。
