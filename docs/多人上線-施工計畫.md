## 二、威脅模型

### 資產（要保護什麼，按嚴重度排）

1. **每位使用者的完整財務資料**（交易、持股、淨值）——洩漏＝隱私災難。
2. **機密欄位**：`ib.flexToken`（IBKR 憑證）、`pdfPassword`／`taishinSecPdfPassword`（＝身分證字號）。目前**明文**存 SQLite——本機可接受（檔案不出門），**上雲前必須加密**（第 6 步）。
3. **帳號本身**（被盜＝1+2 全失守）。
4. 服務可用性（最不重要——個人工具，掛了重開就好）。

### 攻擊者與攻擊面 → 對策

| 攻擊 | 途徑 | 對策（落在哪一步） |
|---|---|---|
| **跨使用者讀寫（IDOR）** | A 改 API 參數讀 B 的資料 | ①每條理財 API（`/api/*`，見 P1-1）伺服器端從 session 取 `user_id`，**絕不信任請求帶的 id** ②Postgres RLS 第二道 ③**全端對抗考題**：A 的 cookie 打 B 的資源必 403（步驟 4、5） |
| 未登入直接打 API | 繞過前端直接 curl | 伺服器端中介層驗 session，**前端隱藏不算防禦**（步驟 4） |
| Session 竊取 | XSS 偷 cookie／中間人 | `HttpOnly + Secure + SameSite=Lax` cookie（JS 讀不到）；HTTPS 由 Render 強制；既有的全站 `esc()` 慣例續用（步驟 3） |
| **CSRF** | 惡意網站帶著你的 cookie 發請求 | SameSite=Lax 擋掉大宗＋**變更類請求驗 `Origin` header**（雙保險；步驟 3 一起做） |
| 邀請濫用 | 猜註冊網址自行開戶 | Supabase 關閉公開註冊；`/register` 無有效邀請 token＝只顯示「需受邀」；邀請 token 由 Supabase 簽發有效期 |
| 憑證洩漏 | secret key 進了前端／git | service_role key 只在 Render env；**repo 加 secret 掃描考題**（grep 樣式牆，步驟 3）；`.env` 進 `.gitignore` |
| 暴力猜密碼 | 對 `/login` 灌請求 | Supabase Auth 內建 rate limit；Render 層不必自建（減法） |
| 惡意輸入 | 超長字串／怪型別打掛服務 | **階段四 B 異常輸入防線**（已排程，William 裁決不降級）＋既有 schema 白名單、null-proto、XSS 跳脫慣例全數續用 |
| **匯入備份覆蓋整包（Codex 複審補）** | `/api/import` 現況＝整包 `saveDb`；多人後可灌別人的／惡意 shape 的備份、或 bug 下覆蓋錯租戶 | HOSTED 匯入**永遠只寫 session user 的 namespace**、匯入檔內任何 `user_id` 一律忽略／拒絕、HOSTED 匯入剝機密欄位、壞匯入不動原資料——**C4 專門考題**（步驟 5） |
| **帳單／IB 解析器 DoS（Codex 複審補）** | 超大 PDF、畸形 XML（entity／壓縮炸彈）、極大量交易列、錯密碼重試 | 每個上傳端點限檔案大小與解析上限、同帳號速率限制、**解析失敗的錯誤訊息不得含密碼／token**——C6 測試項 |
| 資料庫誤刪／寫壞 | 程式 bug、誤操作 | ⚠️ **Supabase Free 不含自動備份（Pro US$25/月才有 7 天）——Codex 複審抓到的事實修正**。初期替代＝雲端版每日排程把使用者資料匯出 JSON 存私有 storage（沿用本機每日備份的思路）；使用者多了再評估升 Pro |
| 依賴鏈 | npm 套件被下毒 | 現況零執行時依賴僅 express＋chart.js＝攻擊面極小，**維持不加框架的紀律**；新增依賴須在 PR 說明必要性 |

### 刻意不防（記錄在案）

- DDoS／大流量攻擊：邀請制個人工具，目標價值低；Render 前面有基本防護，夠用。
- 進階 APT：超出個人專案合理投入。

## 三、最大架構決策：雙模式（需 William 裁決 ①）

**你的本機版每天在用、資料在本機——它不能死，也不該被迫連網。** 建議：

**同一份程式碼、兩種模式，用環境變數切換：**

```
LOCAL 模式（預設，＝現狀）          HOSTED 模式（Render 上）
─────────────────────           ─────────────────────
無登入、監聽 127.0.0.1            Supabase Auth、邀請制
資料＝data/store.db（SQLite）      資料＝Supabase Postgres（按 user_id 隔離）
機密明文（檔案不出門）              機密加密（envelope encryption）
桌面捷徑照常                      noteasy.com.tw
```

- 好處：一份程式兩邊用，修 bug 一次生效；**本機版零改動零風險**（LOCAL 是預設，不設環境變數＝現狀）。
- 代價：資料層要抽介面（`repo.js` 櫃檯後面接兩種後端）——這正是 B1 單一櫃檯當年留下的紅利，改造面積可控。
- 替代案（不建議）：fork 成兩個 repo → 三個月後必然分岔，等於維護兩套。

## 四、資料層設計（SQLite → Postgres，按 user_id 隔離）

- **HOSTED 絕不落回 `data/store.db`**（Render 檔案系統是暫時性的，重部署即消失——Codex 複審提醒）；資料只進 Supabase Postgres。
- Postgres 表沿用現有 kv 形狀起步：`kv(user_id, key, data JSONB)`，主鍵 `(user_id, key)`——**先搬形狀、不改語意**（「搬家與修正分離」既有鐵則）。日後真有多人效能需求再正規化（現況單人 0.5MB，YAGNI）。
- **RLS 政策**：`user_id = auth.uid()` 全表強制——即使 app 層漏了 where 條件，資料庫層也回不了別人的列。
- `repo.js` 介面不變（`getDb`/`saveDb`/…），HOSTED 模式多帶 `userId` 參數——**呼叫端（services/routes）改動面最小化**，逐支 PR 遷移。
- **遷移策略**：不做「線上資料搬家」。上線時 Postgres 是空的→合成資料對抗審查（第 7 步）→通過後你的真實資料用**既有匯出 JSON→匯入**流程進去（一次性、可重來、失敗就清掉重匯）。**回復方案＝本機 store.db 從頭到尾不動**，雲端版砍掉重練都不心疼。

## 五、機密加密（第 6 步）

- 方式：**envelope encryption**——`MASTER_KEY`（32 bytes random）放 Render 環境變數，AES-256-GCM 加密 `flexToken`／`pdfPassword`／`taishinSecPdfPassword` 後才落庫；解密只在伺服器記憶體、只在要用的當下。
- 既有的**機密投影**（`secret-fields.js`：GET 剝除＋`…Set` 布林）原樣續用——加密管 at-rest，投影管不送前端，兩道各管各的。
- 備份／匯出：HOSTED 模式匯出**不含**機密欄位（與本機版「備份必須完整」相反——雲端匯出檔會經過瀏覽器下載，風險不同，刻意不同）。錯誤訊息全鏈路不得含機密（考題掃）。
- LOCAL 模式維持明文（檔案不出門＋現有 .gitignore 保護）——**不動本機版**。

## 五之二、施工契約級決定（C0 r3＝Codex 複審 r2 的 6 個 P1，全數落為契約）

以下六條是 C2–C4 的**施工契約**——實作與這裡不符＝PR 不得合併。

**P1-1 API auth gate 的真實路徑**：現有理財 API 是 `/api/db`、`/api/transactions`、`/api/cards`…**沒有 `/api/finance/` 前綴**（r2 的 URL 表寫 `/api/finance/*` ＝一條都攔不到）。契約：**HOSTED 模式 gate「全部 `/api/*`」，白名單只放行 `/api/auth/*` 與 `/healthz`**；既有路由**不改名**（改名＝動全部前端 fetch，違反最小改動與雙模式零影響）。URL 表據此修正。

**P1-2 request-scoped 租戶狀態**：`userId` 用 **`AsyncLocalStorage`**（node:async_hooks）承載——auth middleware 驗完 session 後 `als.run({ userId }, next)`，repo 後端從 context 取。**fail-closed：HOSTED 模式下 context 缺 userId＝throw**，絕不 fallback 到任何共用資料；LOCAL 模式無 context＝現狀單人。禁止用模組級變數存 userId（跨請求汙染）。

**P1-3 RLS 寫入政策**：政策必須 **`FOR ALL`＝`USING` 與 `WITH CHECK` 兩者都是 `user_id = auth.uid()`**——只寫 USING 只擋「讀」，A 仍能 INSERT/UPDATE 出 B 的列。考題加「A 嘗試 INSERT user_id=B 的列 → 被 RLS 拒絕」。

**P1-4 session 輪替**：用 `@supabase/ssr` 的標準流程——middleware 每請求驗 access token、過期時用 refresh token 換新並**更新 cookie**（rotation）；登出＝revoke＋清 cookie。**不自寫 token 邏輯**。考題：過期 access token＋合法 refresh → 自動續；revoked refresh → 401。

**P1-5 資料庫原子寫入**：kv 整包 JSONB 的 read-modify-write 在兩個並發請求下會互相蓋寫。契約：**`kv(user_id, key, data, version)`＋compare-and-swap**（`UPDATE … WHERE version = :expected`，不中＝重讀重算重試一次、再不中回 409）。C4b 的並發考題據此寫。

**P1-6 Render 監聽位址**：`server.js` 現在寫死 `app.listen(PORT, '127.0.0.1')`——Render 上會**健康檢查連不到、服務起不來**。契約：HOSTED 模式聽 `0.0.0.0`、LOCAL 維持 `127.0.0.1`（本機不對外＝原設計不動）。落在 C2 的模式開關。

### P2（驗收考題／待辦，不擋 C0 合併）
- 上傳端點逐一設檔案大小與解析上限＋同帳號速率限制（C6 對抗測試涵蓋）。
- Cookie 屬性逐項驗收：`HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`、不設 `Domain`（避免子網域外洩）。
- 伺服器 log 保存與輪替政策（Render 內建 7 天，夠用；log 不含機密＝既有考題涵蓋）。
- 依賴掃描：`npm audit` 進 CI；新增依賴須在 PR 說明必要性（威脅模型既有）。
- 上線後監控：Render health check＋Supabase Dashboard 告警（C7 收尾清單）。

## 七、跨使用者對抗考題（驗收底線，C3/C4/C6 分批落地）

1. A 的 cookie 逐一打 B 的每一個集合 API（GET/POST/PUT/DELETE）→ 全部 403，**逐集合列舉、不抽樣**。
2. 無 cookie 打全部 `/api/*`（白名單除外）→ 401；`/finance` 頁 → 轉登入。
3. 偽造／過期 session cookie → 401（不是 500）。
4. 跨站 POST（無 Origin／異 Origin）→ 拒絕。
5. RLS 直連測試：拿 A 的 JWT 直打 Supabase REST 讀 B 的列 → 空結果。
6. 錯誤訊息全鏈路 grep：不含 flexToken／pdfPassword 值、不含伺服器路徑。
7. 邀請 token 重放／過期 → 拒絕。
8. **機密投影逐寫入端驗收（Codex 複審補）**：`GET/POST/PUT /api/cards`、`/api/settings`、`/api/db`、`/api/export`、IB sync 回報、帳單匯入錯誤——HOSTED 全部只准出現 `…Set` 布林、絕無明文機密（本 repo 踩過 POST/PUT 回應洩漏的前例）。
9. **HOSTED 匯入防線（Codex 複審補）**：匯入只寫 session user namespace、檔內 `user_id` 忽略／拒絕、匯入不得帶入明文機密、壞匯入原資料一筆不動。
10. 解析器 DoS：超大 PDF／畸形 XML／極大量交易列 → 明確拒絕不掛服務、錯誤訊息無機密。
