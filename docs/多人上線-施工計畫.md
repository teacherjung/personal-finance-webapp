## 二、威脅模型

### 資產（要保護什麼，按嚴重度排）

1. **每位使用者的完整財務資料**（交易、持股、淨值）——洩漏＝隱私災難。
2. **機密欄位**：`ib.flexToken`（IBKR 憑證）、`pdfPassword`／`taishinSecPdfPassword`（＝身分證字號）。目前**明文**存 SQLite——本機可接受（檔案不出門），**上雲前必須加密**（C5 已完工）。
3. **帳號本身**（被盜＝1+2 全失守）。
4. **服務可用性**——⚠️ **2026-07-28 William 修訂：不再是「最不重要」**。

> **可用性為什麼升級（William 定 2026-07-28）**：原本寫「個人工具，掛了重開就好」，那是**單人自用**的前提。
> 一旦開始邀請別人使用，前提就變了：①別人打不開時**不會自己去重開伺服器**，只會覺得「這個東西不能用」
> ②他們把自己的財務資料交給你保管，「要用的時候拿得到」本身就是保管責任的一部分
> ③你不會 24 小時盯著服務。
> **新排序：可用性仍在 1–3 之後（洩漏比停機嚴重，這點沒變），但不再是「可以不管」的第 4 名——
> 它是上線前要有具體對策的項目**，對策見下方「十、可用性與流量攻擊」。

## 三、最大架構決策：雙模式（需 William 裁決 ①）

**你的本機版每天在用、資料在本機——它不能死，也不該被迫連網。** 建議：

**同一份程式碼、兩種模式，用環境變數切換：**

```
LOCAL 模式（預設，＝現狀）          HOSTED 模式（Render 上）
─────────────────────           ─────────────────────
無登入、監聽 127.0.0.1            Supabase Auth、邀請制
資料＝data/store.db（SQLite）      資料＝Supabase Postgres（按 user_id 隔離）
機密明文（檔案不出門）              機密加密（envelope encryption）
桌面捷徑照常                      noteasy.com.tw
```

- 好處：一份程式兩邊用，修 bug 一次生效；**本機版零改動零風險**（LOCAL 是預設，不設環境變數＝現狀）。
- 代價：資料層要抽介面（`repo.js` 櫃檯後面接兩種後端）——這正是 B1 單一櫃檯當年留下的紅利，改造面積可控。
- 替代案（不建議）：fork 成兩個 repo → 三個月後必然分岔，等於維護兩套。

## 四、資料層設計（SQLite → Postgres，按 user_id 隔離）

- **HOSTED 絕不落回 `data/store.db`**（Render 檔案系統是暫時性的，重部署即消失——Codex 複審提醒）；資料只進 Supabase Postgres。
- Postgres 表沿用現有 kv 形狀起步：`kv(user_id, key, data JSONB)`，主鍵 `(user_id, key)`——**先搬形狀、不改語意**（「搬家與修正分離」既有鐵則）。日後真有多人效能需求再正規化（現況單人 0.5MB，YAGNI）。
- **RLS 政策**：`user_id = auth.uid()` 全表強制——即使 app 層漏了 where 條件，資料庫層也回不了別人的列。
- `repo.js` 介面不變（`getDb`/`saveDb`/…）——**呼叫端（services/routes）改動面最小化**，逐支 PR 遷移。
  ⚠️ **實作沒有走「多帶 `userId` 參數」這條路**（2026-08-02 校正）：租戶身分由 `lib/tenant.js` 的 **`AsyncLocalStorage`** 承載，`getDb()`／`saveDb()` 的簽名裡沒有 `userId`。理由寫在 `tenant.js` 檔頭：模組級變數會被下一個請求覆蓋，**A 的資料會就這樣送給 B**。
- **遷移策略**：不做「線上資料搬家」。上線時 Postgres 是空的→合成資料對抗審查（第 7 步）→通過後你的真實資料用**既有匯出 JSON→匯入**流程進去（一次性、可重來、失敗就清掉重匯）。**回復方案＝本機 store.db 從頭到尾不動**，雲端版砍掉重練都不心疼。

## 五、機密加密（第 6 步）

- 方式：**envelope encryption**——`NOTEASY_MASTER_KEY`（32 bytes random，base64）放 Render 環境變數，AES-256-GCM 加密 `flexToken`／`pdfPassword`／`taishinSecPdfPassword` 後才落庫；解密只在伺服器記憶體、只在要用的當下。
- 既有的**機密投影**（`secret-fields.js`：GET 剝除＋`…Set` 布林）原樣續用——加密管 at-rest，投影管不送前端，兩道各管各的。
- 備份／匯出：HOSTED 模式匯出**不含**機密欄位（與本機版「備份必須完整」相反——雲端匯出檔會經過瀏覽器下載，風險不同，刻意不同）。錯誤訊息全鏈路不得含機密（考題掃）。
- LOCAL 模式維持明文（檔案不出門＋現有 .gitignore 保護）——**不動本機版**。

## 五之二、施工契約級決定（C0 r3＝Codex 複審 r2 的 6 個 P1，全數落為契約）

以下六條是 C2–C4 的**施工契約**——實作與這裡不符＝PR 不得合併。

**P1-1 API auth gate 的真實路徑**：現有理財 API 是 `/api/db`、`/api/transactions`、`/api/cards`…**沒有 `/api/finance/` 前綴**（r2 的 URL 表寫 `/api/finance/*` ＝一條都攔不到）。契約：**HOSTED 模式 gate「全部 `/api/*`」，白名單只放行 `/api/auth/*` 與 `/health`（機器健康檢查，裁決④）**；既有路由**不改名**（改名＝動全部前端 fetch，違反最小改動與雙模式零影響）。URL 表據此修正。

**P1-2 request-scoped 租戶狀態**：`userId` 用 **`AsyncLocalStorage`**（node:async_hooks）承載——auth middleware 驗完 session 後 `als.run({ userId }, next)`，repo 後端從 context 取。**fail-closed：HOSTED 模式下 context 缺 userId＝throw**，絕不 fallback 到任何共用資料；LOCAL 模式無 context＝現狀單人。禁止用模組級變數存 userId（跨請求汙染）。

**P1-3 RLS 寫入政策**：政策必須 **`FOR ALL`＝`USING` 與 `WITH CHECK` 兩者都是 `user_id = auth.uid()`**——只寫 USING 只擋「讀」，A 仍能 INSERT/UPDATE 出 B 的列。考題加「A 嘗試 INSERT user_id=B 的列 → 被 RLS 拒絕」。

**P1-4 session 輪替**：用 `@supabase/ssr` 的標準流程——middleware 每請求驗 access token、過期時用 refresh token 換新並**更新 cookie**（rotation）；登出＝revoke＋清 cookie。**不自寫 token 邏輯**。考題：過期 access token＋合法 refresh → 自動續；revoked refresh → 401。

**P1-5 資料庫原子寫入**：kv 整包 JSONB 的 read-modify-write 在兩個並發請求下會互相蓋寫。契約：**`kv(user_id, key, data, version)`＋compare-and-swap**（`UPDATE … WHERE version = :expected`，不中＝重讀重算重試一次、再不中回 409）。C4b 的並發考題據此寫。

**P1-6 Render 監聽位址**：`server.js` 現在寫死 `app.listen(PORT, '127.0.0.1')`——Render 上會**健康檢查連不到、服務起不來**。契約：HOSTED 模式聽 `0.0.0.0`、LOCAL 維持 `127.0.0.1`（本機不對外＝原設計不動）。落在 C2 的模式開關。

## 十、可用性與流量攻擊（William 定 2026-07-28：「應該要防就要防」）

### 先講一句實話：**app 的程式碼擋不住真正的 DDoS**

大流量攻擊是在「你的程式跑起來之前」就把頻寬與連線塞爆的。不管我在 `server.js` 裡寫什麼，
封包已經到了 Render 的機器上、已經佔用了它的連線數。**這件事只有「在你的服務前面再擺一層」才擋得住。**

所以下面刻意分成三層，各自寫清楚「防得到什麼、防不到什麼」——不含糊帶過。

### 第一層：app 自己擋得住的（我可以直接做）

| 項目 | 防得到什麼 | 狀態 |
|---|---|---|
| **大件 body parser 移到身分牆之後** | 未登入者無法讓伺服器先吞 50MB。實測：10 個未登入請求 × 45MB 從「行程 OOM 死亡」變成「全部 401、記憶體 +8MB」 | ✅ 已修 |
| **登入端點速率限制**（同 IP） | 暴力猜密碼；連續打登入把行程拖垮。20 次／5 分鐘 | ✅ 已修 |
| **上傳／解析端點速率限制**（同帳號） | 已登入者反覆丟大 PDF 把 CPU 佔滿（**多人化才成立的攻擊面**：以前只有你自己會這樣做）。30 次／5 分鐘 | ✅ 已修 |
| **對外連線端點速率限制**（同帳號） | 猛打 `/api/ib/sync`（6 次／5 分）與 `/api/quotes`（60 次／5 分）＝**拿我們的伺服器去打 IBKR 與 Yahoo**，可能害使用者的 Flex Query 被對方限流甚至停用 | ✅ 已修 |
| **計數器自己的記憶體上限** | `sweep` 每個窗口最多跑一次，兩次之間攻擊者高速換 IP 可以塞進幾百萬個鍵——「防資源耗盡」自己成了資源耗盡的來源。每顆計數器 `maxKeys` 10000＋O(1) 淘汰 | ✅ 已修 |
| **解析器資源上限**（PDF 頁數 200／文字節點 30 萬／**XML 12MB**／IB 列數 5 萬） | 壓縮炸彈、畸形 XML、極大量列。**檔案小不代表解析便宜**——200KB 的 PDF 可以有幾萬頁 | ✅ 已修（⚠️ **XML 是 12MB 不是 40MB**——2026-07-28 從 40 降到 12，因為 **40MB 正是實測會讓行程 OOM 死掉的線**：12MB→峰值 254MB、24MB→387MB、40MB→死。單一真相＝`lib/parse-limits.js` 的 `MAX_IB_XML_CHARS`） |
| **慢速連線（slowloris）逾時** | 宣告很大的 Content-Length 卻只滴幾個位元組，把連線佔住。HOSTED 收緊成 header 20s／請求 **270s**／keep-alive 10s（Node 預設 60s／300s／5s）。⚠️ requestTimeout 是「收完整個 request 的總時間」不是 idle——舊值 120s 配 50MB 上限＝隱形要求 437KB/s，實測 300KB/s 的上傳在 120 秒被切斷、只收到 36MB，**正當的大備份還原被誤殺**。新值由「50MB ÷ 最慢可接受上傳速度 200KiB/s」除出來。slowloris 的本體是 header，由 20s 那條擋著 | ✅ 已修 |
| **IB 那條路的三個洞** | ①`res.text()` 把任意大小的回應整包吃進記憶體，上限檢查跑得太晚 ②列數等 `parse()` 展開成物件才數，而且**完全沒數 `OpenPosition`**（20 萬筆持倉暢行無阻）③列數每份 statement 各自檢查，10 份 × 各 3 萬筆＝總量 30 萬筆全部放行 | ✅ 已修 |
| **PDF 抽取器的資源洩漏** | 上限一 throw 就跳過 `task.destroy()`，pdfjs 的 worker 留著不放——「防資源耗盡」的路自己在漏資源，而且**只有被攻擊時才會發生** | ✅ 已修 |
| PDF 壓縮炸彈 | 單頁、1000 個文字節點、解壓後 500MB 的 PDF——頁數牆與節點牆**都摸不到它** | ✅ **已修**（2026-08-02 校正：這一列原本寫「刻意不做、`streamTextContent` 零收益 640MB vs 640MB」——**那個結論是錯的，程式早就做了**）。兩層：①`readPageTextCapped` 用 `streamTextContent()` **邊收邊數、超標當場 `cancel()`**（`lib/parse-limits.js`，兩種模式都套）②HOSTED 走**行程級隔離**（`lib/pdf-isolate.js`，#350／#373）。⚠️ 「零收益」那句話 `lib/parse-limits.js` 的註解自己就標明是錯的——別再照它把 `streamTextContent` 拿掉。考題 `test/parse-limits.test.js`＋`test/pdf-isolate.test.js` |

> Supabase Auth 本身有內建登入速率限制，所以「暴力猜密碼」已有一層；上面那條是**保護我們自己的行程**。

**第 3 題的理由與觸發條件（這題最需要講清楚）**

Pro 是 US$25/月，是 Render 的 3.5 倍，換到的是「7 天 PITR 備份＋不會自動暫停」。現在不值得，因為：

  雲端整個消失，你從 Mac 重新匯入就好——這正是 C0 寫的「回復方案＝本機 store.db 從頭到尾不動」。
- 「一週無活動自動暫停」用每日活動就解掉，不必花錢。

⚠️ **但這個理由有一個明確的失效點，寫下來免得忘記**：

> **第一個「不是 William」的使用者真的開始記帳的那一刻，這個理由就不成立了**——
> 他的資料在雲端**沒有本機副本**，Free 方案的「無自動備份」就從「可接受的取捨」變成
> 「幫別人保管資料卻沒有備份」。**那一刻立刻升 Pro**，不要等出事。

配套（都可以做在程式裡，不必花錢）：
1. **每日喚醒＋每日雲端匯出**：排程每天打一次會查資料庫的端點（同時解掉自動暫停），並把每位使用者的資料匯出存檔。
   ⚠️ C5 之後**雲端匯出不含機密**，所以那份備份還原後要重輸 IB token 與 PDF 密碼各一次——這是刻意的。
2. 匯出失敗要**出聲**（比照本機每日備份的 `backupFailStreak`：靜默失敗的備份比沒有備份更危險）。
