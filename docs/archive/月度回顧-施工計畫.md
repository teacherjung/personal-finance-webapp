## 〇、一句話與已鎖定的決定

**定位**：總覽一張「後照鏡」卡，回答「最近花太兇嗎、花在哪、有沒有透支」，**全用已結清資料**，繞開信用卡帳單的時間差。

| 決定 | 拍板 |
|---|---|
| ① 近六月花費**直條圖** | 只前六個**已結清**月，**不含本月** |
| ② 分類佔比 | **先大分類**（金額＋%）；點開才顯示**子分類**（金額＋%） |
| ③ 收支透支 | 收入有沒有 cover 支出＝**現金流視角**，透支紅字 |
| ④ 淨值 | **不放**（留在資產配置頁） |
| 退款 | **配對抵減**：配到前期消費→抵該消費月；配不到→不計入、角落小字提示 |
| 部分退款 | v1 **精準配、配不到擱著**（不亂抵） |
| 未對應退款 | **回顧卡角落一行小字** |
| 落點 | **總覽卡** |

**三個必懂前提**
- **前提 A**：退款配對抵減是 money-critical 連帶改動（改帳單匯入），**且過去六個月要重匯帳單才會反映**（已匯入的舊資料沒有退款）。
- **前提 B**：卡上兩把尺——①②＝**消費視角**（含刷卡、不含繳卡費）、③＝**現金視角**（含繳卡費、不含刷卡）。兩者「支出」數字**本就不同**，要標清楚、別讓人以為算錯。
- **前提 C**：淨值不在此卡；它是投資漲跌與匯率主導的雜訊，對「花太兇嗎」沒幫助。

## 一、使用者需求

- **使用者**＝老師本人（回顧型、單人；多人化是階段 C 以後）。
- **要回答**：①這半年花錢高低起伏？②某月錢去了哪幾大類、各佔幾 %（想深入再看子類）？③某月是結餘還是透支？
- **為何適合**：比的是已結清、帳單已到的月份，不需即時資料——正好避開時間差。
- **成本低**：現金流（`computeCashflow` 已存在）、分類統計都現成；只差「兩帳聯集＋退款配對」這個新積木。
- **v1 不做**：淨值與其拆解（候選 1-5）、年度回顧（1-3）、Tier 2 部分退款模糊配對、圖表花俏化。

## 二、操作流程

1. 總覽新增「月度回顧」卡。
2. **①直條圖**：六根＝過去六個已結清月（例：現在 7 月中 → 顯示 1–6 月），每根＝該月**總消費**（消費視角、已抵退款）。本月不畫。
3. **點某根長條 → 選定該月**；②③ 跟著更新。**預設選最右邊那根（最近已結清月）**。
4. **②分類佔比（選定月）**：大分類清單（金額＋% of 該月總消費＋佔比條），每列可**點開**看子分類（金額＋%）。
5. **③透支（選定月）**：收入 / 支出（現金流）/ 淨額；**透支時紅字**「本月透支 −X」。
6. **角落小字**：「另有 N 筆退款（共 X 元）找不到對應消費、未計入」（tooltip 列出是哪幾筆）。
7. 頂部白話一行：「6 月花了 X，比 5 月多 Y；最大宗飲食 35%；當月結餘 +Z。」

## 三、資料來源與計算口徑

| 區塊 | 資料來源 | 依據（現況） | 納入／排除 |
|---|---|---|---|
| ①六月直條 | 新積木 `consumptionByMonth(db)` 的各月總額 | — | `type=expense`、**兩帳都算**（`isCardTx` 真假都收）、排除繳卡費（空分類）、**退款配對抵減**、無日期跳過、`monthKey(date)` 歸月 |
| ②大＋子分類% | 同積木的選定月兩層彙總 | — | 分母＝該月總消費；空子類→「（未分子類）」一格、不丟；未分類/其他＝獨立一格算進分母 |
| ③收支透支 | `computeCashflow(db, mk)` | [derive.js:189](../../lib/derive.js) | 現金視角：只 income/expense、排除卡帳、含繳卡費 |
| 淨值 | **不取用**（在資產配置頁） | [derive.js computeAssets](../../lib/derive.js) | — |

**新積木 `consumptionByMonth(db)`（純函式，放 `lib/derive.js`）**
- 輸入：整庫交易（**要全庫**，因為退款可能跨月配對）。
- 步驟：①取所有 `type=expense`、排除繳卡費（空分類）②分成「消費（正）」與「退款候選（負、非繳款）」③跑退款配對（見第四節）④把配到的退款抵到**對應消費的月份＋分類**⑤彙總成 `{ byMonth: { 'YYYY-MM': { 大類: { total, subs:{ 子類:金額 } } } }, unmatchedRefunds: [{date,amount,store}] }`。
- 回顧端點讀「最近六個已結清月＋選定月」＋`unmatchedRefunds`。
- **與分類預算共用**：未來若補上電子發票、要做即時預算，這個積木直接重用。

## 四、退款配對抵減引擎（money-critical 核心・完整規格）

### 現況（要改的三處）
- [statement.js:668](../../lib/statement.js) `finalize`：所有負數一律 `isPayment`、category=`繳款/退款`。
- [statement-import.js:147](../../lib/services/statement-import.js)：`amount > 0` 才收 → 繳款與退款**都被擋掉**。
- 目前**沒有**繳款關鍵字的單一真相（只有 `isServiceFee` 這個 pattern 前例，[statement.js:661](../../lib/statement.js)）。

### 要改成
1. **新增單一真相 `isCardPayment(desc)`**（比照 `isServiceFee`）：匹配繳款關鍵字（自動轉帳扣繳／信用卡款／感謝繳款…）。
2. **`finalize`**：負數且 `isCardPayment` → 仍當繳款、**不匯入**；負數且非繳款 → **當退款候選**匯入（`type=expense`、金額保留負號、帶 `storeKey`、`refundOf=null`）。
3. **匯入閘門**：放行「非繳款的負數」，繼續擋繳款與 `>1e8` 誤抓。
4. **配對在彙總時（`consumptionByMonth`）算，不在匯入時凍結**。

### 配對階梯（每次彙總用當下全部資料重算）
1. 已被繳款關鍵字擋掉的不進來。
2. 對每一筆退款候選，往前找符合**全部**條件的消費：**同卡 ＋ 同 `storeKey`（品牌身分）＋ 金額精準相符 ＋ 消費日較早 ＋ 尚未被別的退款配過**。
   - **配到** → 確認是退款；抵減記到**該筆消費的 `monthKey(消費日)` 與分類**。
   - **配不到** → **不計入回顧**；收進 `unmatchedRefunds`（角落小字）。
3. **一對一**：配到就把該消費標記為已被抵，避免重複。
4. **v1 精準配**：退款金額 ≠ 任何單筆消費（部分退款）→ 歸未對應、先擱（寧少抵不亂抵）。Tier 2（`退款 ≤ 消費剩餘額` 模糊配）留待日後視需要。

### 為什麼「彙總時配對」
使用者可能**先匯 7 月（含退款）、後補匯 5 月（原購買）**。若匯入當下凍結「配不到」，補了 5 月也救不回。彙總時重配 → **自動自癒**、可重算、好測。

### 為什麼天然不會「負數變收入」
- 配到的退款一定 ≤ 它抵的那筆消費 → 該月該類**不被單一退款壓成負**。
- 配不到的**直接不算** → 不會有孤兒負數讓某月看起來像進帳。

### 存法（誠實）
退款照實存進卡帳：**真實退款日期**＋`storeKey`＋負數金額＋`refundOf` 標記。配對與消費月歸屬**全在 `consumptionByMonth` 裡算**。好處：信用卡明細頁的**帳單對帳**（明細 vs 應繳）維持誠實日期，回顧的「消費月份抵減」由彙總層負責——兩個鏡頭各得其所。

## 五、可能讓金額算錯（或被當算錯）的風險

| # | 風險 | 後果 | 防法 |
|---|---|---|---|
| R1 | **兩把尺混淆**（③支出 ≠ ①②消費總額） | 被當 bug、失去信任 | 分區標鏡頭、白話說明各答什麼 |
| R2a | **繳費被當退款**（沒關鍵字又剛好同額） | 整筆卡費灌進某類、爆負 | 同卡＋同 storeKey＋同額三重條件；繳費無店名、storeKey 對不上→天然配不到 |
| R2b | **退款配到錯的消費**（同店同額多筆） | 只差「哪個月」，金額/類別對 | 影響小；配最近未配的那筆 |
| R2c | **部分退款漏抵** | 該類消費偏高（毛額） | v1 明示歸「未對應」並顯示總額、不靜默；需要再開 Tier 2 |
| R2d | **重複抵減** | 一退款抵多筆／一消費被多退款抵 | 一對一標記；考題鎖 |
| R2e | **匯入順序**（先退款月後購買月） | 一度配不到 | 彙總時配對＝自癒；考題驗自癒 |
| R3 | **消費帳本範圍抓錯**（只一本帳） | 漏算刷卡或銀行支出 | 兩帳聯集 |
| R4 | **繳卡費被當一個分類** | 與刷卡明細重複算 | 空分類／「繳款退款」排除在②外 |
| R5 | **半匯入／未匯入月＝短長條** | 假象「這月省很多」 | 偵測偏低/空的月，標「帳單可能未匯入」，不當真低 |
| R6 | **佔比分母**（負值/未分類被藏） | % 說謊 | 負值夾 0 或標註；未分類/其他當獨立一格算進分母 |
| R7 | **空子類被丟** | 子類%加不到 100% | 空子類歸「（未分子類）」一格 |
| R8 | **proto／月界／台幣以外** | 聚合走樣 | `Object.create(null)`／`monthKey(parseLocalDate)`／台幣守門（沿用既有防線，AGENTS 3.5） |
| R9 | **③「透支」時間錯位** | 本月現金大出＝繳上月卡費 | 白話註明③是「現金進出」，與②消費不同步是正常 |
| R10 | **退款在信用卡明細頁的知外效應** | 明細頁 byCat（[transactions.js:41](../../public/modules/transactions.js)）把退款當負數列在帳單月，某類可能顯示怪異負值 | 動工時確認該頁呈現；必要時該頁也套配對排除，或明示「原始帳單視角」 |

## 六、邊界情況

- **資料不足六個月**：有幾根畫幾根，不補零假月。
- **某月完全沒交易**：長條 0 但標「無資料」（與「真沒花錢」區分）。
- **退款配到、但購買月在六月窗外**（如 8 個月前）：資料層正確抵減該老月，圖上不顯示、不產生幻影。
- **新出現／消失的分類**：以選定月為準；「上月大額、這月沒有」在直條圖看得出。
- **還原舊備份**：`/api/import` 整包取代，舊資料可能無退款／斷層 → 照現況畫、不假裝抵減。
- **本月被點選**（若允許）：明顯標「帳單可能還沒到、未齊」。

## 七、驗收標準

1. 總覽「月度回顧」卡：①六根已結清月長條（不含本月）②選定月大分類金額與%＋可點開子分類③收入/支出/淨額＋透支紅字④角落「未對應退款」小字。
2. 點長條切換選定月；預設最近已結清月。
3. 退款配對抵減生效：5 月買、7 月退 → **5 月**該類淨額下降、7 月不受影響；配不到 → 不計入、進角落小字，**沒有任何月變負**。
4. ③支出與①②消費總額允許不同且畫面說明；②的%加總＝100%（含未分類/未分子類）。
5. 短/空月標「帳單可能未匯入」；不足六月不補假月。
6. **每個「必須懂的概念」都有 `.info-link` 就地白話解釋**（清單見第十一節）、文案經老師審定；瀏覽器唯讀實測點開 `openInfo` 顯示正確。

## 八、應補的測試題目（隔離 DB、`node --test`）

**退款配對（最關鍵）**
- ✅ 繳款關鍵字負數→不匯入；非繳款負數→匯入為退款候選。
- ✅ 5 月買 500、7 月退 500 →**5 月**該類淨額 0、7 月不變。
- ✅ 配不到（購買月沒匯）→ 不計入任何月、進 `unmatchedRefunds`，**沒有任何月變負**。
- ✅ 自癒：先匯 7 月（退款）算＝未對應；補匯 5 月後重算＝自動抵到 5 月。
- ✅ 部分退款（退 200、原購 500）→ v1 歸未對應、不亂抵。
- ✅ 一對一：兩筆同額退款不會都抵到同一筆消費。
- ✅ 大額繳款無關鍵字（保險）→ 不被當退款配對。

**六月直條＋分類%**
- ✅ 每月長條＝該月兩帳聯集消費（已抵退款）；排除繳卡費；月界（12/31 vs 1/1 本地日）。
- ✅ 大類%加總 100%（含未分類）；子類%加總 100%（含未分子類）；空子類不掉。
- ✅ 某月無資料→標記而非畫 0 假象。
- ✅ proto（`__proto__` 等以 `JSON.parse` 造鍵）／僅台幣。

**透支（③）**
- ✅ `computeCashflow` 淨額正負正確；透支旗標正確。
- ✅ ③支出 ≠ ①②消費總額（有刷卡時）＝鎖住「兩把尺」事實。

**端到端**
- ✅ 種六個月交易（含跨月退款）＋呼 `GET /api/monthly-review` → 直條/分類%/透支/未對應退款全對（防「兩端測、中間沒測」）。

- **機密投影不受影響**：本功能不碰 `pdfPassword`/`flexToken`，但沿用既有投影規矩。
- **帳本判準單一真相**＝`isCardTx`（[categories.js:66](../../public/modules/categories.js)）；讀現金流一律用它排除 card。
- **原型污染**：分類/店鑰匙/店名是使用者文字，聚合一律 `Object.create(null)`、查表 `hasOwn`（AGENTS 3.5、`lib/safe-map.js`）。
- **金額格式**：統計大數字 `wan()`、明細 `money()`；負號 U+2212。
- **排序**：沿用 `public/modules/tx-sort.js`（絕對值排序＋日期次鍵）。
- **同步點**：新增繳款關鍵字 `isCardPayment`＝單一真相 export，勿在多處各寫一份。

## 十一、頁面上要向使用者解釋的事（.info-link／openInfo）

**使用者鐵則（2026-07-22）**：凡是「使用者必須懂、否則會把**正常**數字當成**算錯**」的概念，**一律在網頁上就地用白話解釋**（現成 `.info-link`＋`openInfo`，AGENTS.md UI 慣例），不能只放文件、也不能假設使用者自己懂。**文案 Claude 起草、老師審改**。這也是教學功能線「情境式名詞解釋」的第一批就地解釋。

| 放哪 | 標題 | 白話內文（草稿，待老師審） |
|---|---|---|
| ②消費 ＆ ③現金流 標題旁 | 「消費」和「現金流支出」差在哪？ | 「消費」＝你買了多少東西（不管刷卡或現金），**不含**繳卡費那一筆。「現金流支出」＝銀行帳戶這個月實際流出多少，**含**繳卡費、**不含**刷卡明細。同一件事兩個角度、數字本來就不一樣，兩個都對：想知道「錢花在哪」看消費，想知道「這個月現金夠不夠」看現金流。 |
| ①直條圖 標題旁 | 為什麼沒有「本月」？ | 刷卡消費通常要等一個多月後、帳單來了才看得到。本月資料還不齊、現在算會失真，所以這張圖只放**已經結清**的月份，每一根都比較實在。 |
| 角落「未對應退款」小字旁 | 退款是怎麼算的？ | 退款會自動去找它對應的那筆消費，把錢**退回你當初買的那個月**，這樣每個月的花費才準。如果找不到對應消費（例如那個月的帳單還沒匯入），就先**不計入**，免得某個月憑空多出一筆退款、看起來像多賺錢。這幾筆就是還沒找到對應的，補匯那個月帳單後會自動歸位。 |
| ③透支／淨額旁（透支時） | 「透支」是什麼意思？ | 這裡的透支說的是**現金週轉**：這個月流出的錢，大部分其實是在繳**上個月**的卡費。所以「這個月透支」不一定是這個月亂花——想看這個月花在哪，看上面的「消費」分類。 |
| 被標記的矮長條 tooltip | 這個月花很少？ | 這個月看起來特別低，可能是那個月的帳單還沒匯入、**不是真的省**，補匯之後就會更新。 |

實作：沿用 `openInfo`／`.info-link`（無底線、hover 珊瑚色）；文案抽成可維護的常數（老師審定前用草稿）。**每個「必須懂的概念」都要有對應的 info-link，缺一即未達驗收（見第七節）。**
