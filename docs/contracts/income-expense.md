## 月度回顧的消費口徑與退款配對

**改這裡**：月度回顧的消費口徑與退款配對

**記得同步這裡**：**配對本體＝`lib/derive.js pairRefunds(db)`（單一判準，2026-07-27 拆出）**，月度回顧的加總＝`consumptionByMonth(db)` 呼叫它；信用卡費頁的消費歸屬與兩端標記走 `GET /api/refund-pairs`（同一個 `pairRefunds`）。**配對規則只能改 pairRefunds** ——分成兩份實作就會走散（同一筆退款兩頁抵到不同月）。`consumptionByMonth` 的抵減順序＝pairRefunds 的配對順序（退款日→id），`add` 有 `Math.max(0,…)` 夾底，順序會影響結果、拆分時逐字保留。以下口徑不變：消費視角收信用卡＋現金流兩帳的 `type:'expense'`，排除空分類繳卡費、非台幣與壞日期。退款每次彙總重配「**同卡（stmtRef 卡 id 優先）＋同「配對身分」＋金額精準相符＋消費日較早＋未被配過**」的最近消費（⚠️ **配對身分不是 storeKey**：加油站／停車費／運動中心是**彙總鑰匙**（清單＝`statement.js AGGREGATE_STORE_KEYS`；**字面聚合在 `KEY_AGGREGATE_RULES` 加一條＝必須同步加進這個 Set**，2026-07-27 運動中心入列時通用化），用它會讓不同店家撞成同一把——退六月嘟嘟房那筆會被算到七月普客二四頭上，金額歸錯月份（Codex 複審 2026-07-26 重現；**同型錯配在加油站上早就存在於 main**）。改用 `statement.js refundPairKeyOf(原文)`：彙總類用「清理後的顯示名」當細身分（`加油站（泰山）`≠`加油站（新店）`、`嘟嘟房（台北101）`≠`台灣普客二四`），其餘店家維持品牌鑰匙（Klook 型退款照舊配得到）；沒有原文（手動記帳）時 `refundPairKeyOfStoreKey` 讓彙總鑰匙一律**不可配對**＝列未對應。考題＝`test/refund-pairing-aggregate.test.js` 跨月同卡同額不同站四情境），一對一抵回原消費月與原分類；部分／孤兒退款不猜、不算進任何月，列 `unmatchedRefunds`。該函式只推導不改 db，`GET /api/monthly-review` 只能呼叫 `buildMonthlyReview`，不另寫公式。分類／子類是使用者文字，彙總 map 必須 null-proto。**兩把尺不可混**：長條／分類用消費視角；透支仍用 `computeCashflow` 現金流視角。預設選最近一個**實際消費金額大於 0**的已結清月（最新月尚未匯帳單時不先顯示空白），但使用者明點空月仍尊重；摘要比較同樣往前跳過空月，找最近有消費的月份。

## 信用卡費頁的兩種口徑

**改這裡**：信用卡費頁的兩種口徑（使用者定 2026-07-27）

**記得同步這裡**：同一頁刻意並存兩種算法，改動前先讀懂：**上半部（「本月消費」數字＋消費分類長條）＝消費歸屬**——消費算消費當月、配對成功的退款回頭抵減**原消費那個月的那一類**（用原消費的分類，不是退款自己的分類）、未對應退款完全不計入；**下半部明細列＝帳面原貌**，日期照帳單走、金額照帳單印，才對得起銀行帳單。**所以圖表加總 ≠ 明細加總，是刻意的**，不可「修好」。純函式積木＝`public/modules/refund-attribution.js`（零相依，考題 `test/refund-attribution.test.js`），`transactions.js` 只接線；配對結果一律向後端 `GET /api/refund-pairs` 拿，**前端不得自寫配對規則**。兩端標記（退款列「（原消費月）」、消費列「已退 N」）是**純呈現**：絕不寫進 `note`／`storeKey`（寫進去會被當分店括號，下次整理店名就切爛）。配對表抓不到時退回帳面口徑並在畫面明說——靜默降級會讓兩種口徑長得一模一樣、看不出數字換過。未對應退款要在畫面列出（金額憑空消失比數字難看更危險）。

## 銀行收支真學習的方向與內轉子分類

**改這裡**：**銀行收支「真·學習」的方向與內轉子分類**（Codex r13#2/#4）

**記得同步這裡**：銀行交易匯入時存**不可竄改的 `dir:'in'\|'out'`**（`FIELD_SCHEMA` 有型別、**不進 CRUD 白名單**＝使用者改分類也不動它；amount 無正負、type 又可被改錯，唯 dir 忠實記錄錢進錢出）。①**「同類一起改」`applyLearnedBankToExisting` 逐筆過方向護欄**：收入規則只套進帳、支出只套出帳、內轉可兩向但子分類依**本筆方向**重播，回 `{changed, skipped}`，前端筆數與 toast 只算/只報可安全套用者——**不可整批套同一 cls**（同鑰匙可同時有進帳與出帳，會把出帳無聲改成收入＝毀現金流，生存優先）。⚠️**方向來源優先序（`txDirection(db,t)`，Codex r13 複審#1）**：①存好的 `dir` ②**`bankRef` 的原始方向**（台新格式 `bank\|帳號\|日期\|方向\|…` 第 4 段、他行 `bank2\|機構\|帳號\|日期\|方向\|…` 第 5 段——`bankDirFromRef` 雙軌解析，P1a r1#4；匯入寫死不隨改分類而變）③最後才從 type/子類推——舊批次可能留下「bankRef=out 但子類=內轉入」的不一致，只靠 type/子類會把出帳誤判成 in、被收入規則改掉；用 bankRef 讀時解析（不必一次性搬家補 dir，bankRef 已是同一份事實）。②**內轉子分類一律用角色重播 `replayTransferSub(db, sub, dir)`**（out/in 角色隨本筆方向取現名、settle 方向中性保留、自訂原樣）——**不可字面比對「交割」/「內轉出」**（角色改名後字面就對不上，把交割誤翻成內轉出/入）。角色查詢集中在 `categories.js transferSubRole`（預設 token role-first，同 `conformTransferSub` #184）。

## 同類同店一起改是單一原子指令

**改這裡**：**「同類/同店一起改」＝單一原子指令**（護欄 G3，2026-07-22）

**記得同步這裡**：「編輯這一筆＋套到同鑰匙其他筆」是**一個使用者操作**，必須**一次寫檔**（全有或全無）——不可前端「先 PUT 再另呼 apply」兩次寫（中途失敗＝半套用，且原本 transactions.js/settings.js 沒接第二次呼叫的錯誤）。實作：傳播邏輯抽成**純 in-db 工作函式**（不自己 `saveDb`）＝`applyCategoryToStoreDb`（帳單/storeKey）、`applyLearnedBankToDb`（銀行/bankKey）；原子入口＝`PUT /api/transactions/:id` 帶 `applyAll:true`（`crud.js` 在同一 `updateItem` 的 `beforeSave` 內：先 `learnFromTxEdit` 學、再跑對應 worker 傳播）＋`renameStoreDisplay(..., applyAll)`（設定頁）。傳播丟 apiError（保留字/找不到目標）＝整筆編輯一起 rollback（`save` 還沒跑）。回應多帶 `applied` 計數給前端報數（帳單 `{changed,origCleared}`／銀行 `{changed,skipped}`——含方向護欄略過數）。**標準端點 `/statement/apply-category`、`/bank-tx/apply-learned` 保留為維護/相容薄殼**（讀→worker→寫；`applyCategoryToStore`/`applyLearnedBankToExisting` 也是薄殼），前端主流程不再用它們。**改傳播邏輯＝改 worker（原子路徑與薄殼共用同一份）**；`applyAll` 是控制旗標、非可寫欄位（`crud.js` 先摘掉再過白名單）。

使用者填的截斷寫法」的選擇**（完整版排前面）：只比截斷版的話「禾豐日式料理-林口店」會在「禾豐日式料」處切開、剩下「理-林口店」不是合法分店而被丟掉（內建規則靠 `(店)?` 這種選擇性群組解決，使用者不會也不該寫 regex → 由編譯器補）。⚠️**寫入端要嚴格、櫃檯端要寬鬆**（Codex r3#6）：`sanitizeStoreRules` 寬鬆（壞的丟掉繼續跑）是給**櫃檯與匯入舊備份**用的——不能讓一條壞規則卡死資料庫；但**使用者按儲存**這條路完全相反，寬鬆的結果是「型別打錯 → 當成空物件 → 回報成功 → 把手上全部規則清空」。所以 API 走 `validateStoreRulesStrict` 先驗形狀，有問題整包 400、什麼都不動；非法 `mode` **明確報錯**不可默默降成最寬的 `contains`（拼字錯誤會讓規則命中一大票店家）。⚠️**`rename` 必須冪等**（Codex r3#5）：整理會重複執行（規則指紋變動、開 app 自動跑），`ABC→台灣ABC` 跑兩次變 `台灣台灣ABC`、無限膨脹 → **`to` 含有 `match` 的規則一律拒收**。⚠️**原型鍵用 `Object.getOwnPropertyNames(Object.prototype)` 全擋**（`isProtoKey`，Codex r3#4）：只擋 `__proto__`/`constructor`/`prototype` 不夠——`toString`/`hasOwnProperty`/`valueOf` 一樣會讓 `learnedCategories[key]=…` 去碰原型而不是建立鍵，那條學習人間蒸發（Codex 實測 `toString` 可過驗證、整店改分類回報成功但學習沒存下來）。**⛔ 核心不變量：`CATEGORY_RULES`（分類規則）刻意不開放編輯**——`storeKeyOf` 用 `categorize(原文)` 判「油錢→加油站」，分類可編輯的話改一條分類就讓身分鑰匙漂移、既有學習全部對不上；**鑰匙的判定基礎凍結在內建規則**（`test/store-rules.test.js` 兩題鎖住）。使用者要改分類仍走「同店一起改」（學習表），那條路不動鑰匙。 ⚠️**跨規則也要冪等**（Codex r4#4）：單條規則自我冪等（`to` 含 `match`）不夠——`甲→乙`＋`丙→甲` `STORE_CANON`（那張表只在 cleanStore 開頭比對原文），rename 產物若是內建標準名的別種寫法（`STARBUCKS SHOP`），未來哪張帳單直接印這串字會被 canon 清成「星巴克」＝同一家店兩種口徑、兩把鑰匙。判準比**品牌身分**（`storeKeyOfName(cleanStore(to)) !== storeKeyOfName(to)` 才拒）——cleanStore 會摘尾端「（分店）」，帶分店的合法目標（統一超商（百福））是裝飾差不是漂移，不可誤殺。⚠️**非法 `mode` 整條剝除**（Codex r4#6）：`sanitizeStoreRules` 遇 mode 有值但拼錯（`containz`）**丟掉整條並記 bad**，不再默默降成最寬的 `contains`（拼字錯誤會命中一大票店家）；mode ## 規則入櫃檯

**改這裡**：**「規則入櫃檯」**（第三帖）：`lib/repo.js` 每次讀取都把 `settings.storeRules` 餵給 `store-rules.js` 的模組級單例

**記得同步這裡**：`statement.js` 是純函式模組（測試直接 import、不碰資料庫）不能自己讀 settings。比照 B3「驗證入櫃檯」裝在唯一的門上：**任何要用店名規則的程式碼一定得先向櫃檯拿資料**，所以結構上不可能忘記同步、也不必為此多讀一次檔（值沒變時 `setUserRules` 只比一小段 JSON 就返回）。⚠️**repo.js 內所有讀取一律走 `loadSynced()`，不要直接呼叫 `load()`**——漏一處就有路徑拿到過期規則。⚠️**「不可逆的變更」有兩種，預覽都要講、UI 的「什麼都沒改」判斷也要含它們**（自審 r3＋Codex r3#2，高）：①`learnedConflicts`＝併鑰匙時兩邊教過的分類只留得下一個 ②`learnedNameChanges`＝學過的**自訂店名**被新規則改寫或清除（更隱蔽：孤兒學習的自訂名被改時 `changed`／`keyChanged` 都是 0，前端若只看這兩個數字就會早退並顯示「不會改動任何既有記錄」，使用者放心按下去、取好的名字就沒了）。**衝突判定用 `Object.hasOwn` 不可用 truthy**（Codex r3#3）——空字串子類是合法值（＝不分子類，使用者拍板），truthy 判斷會把它當「沒有值」而漏報，合併後 `''` 蓋掉 `'餐廳'` 卻無人警告。⚠️**預覽失敗時不可繼續儲存**（Codex r3#7）：安全帶斷了就該停車。⚠️**預覽必須把「學習表的效果」也算出來**（自審 r3，高）：`normalizeBranches` 的學習表區塊以前整段包在 `if (!dryRun)` 裡，而**併鑰匙會蓋掉學過的分類、且刪掉規則也救不回來**——那是整個自助化唯一不可逆的效果，預覽卻對它完全盲目。現在只有「寫入」跳過 dryRun，計算照跑，回傳 `learnedConflicts`（兩邊都有值且不同的欄位＝真衝突；缺一邊只是互補，不打擾使用者）；UI 在預覽窗顯示 `.rule-warn` 警告，直接按「儲存並套用」也會先偷跑一次預覽、有衝突才 confirm。⚠️**預覽必須用 `setRulesOverride`（覆蓋層）而非 `setUserRules`**：預覽內部會 `getDb()`，候選規則放在「櫃檯值」那層會被當場洗掉、預覽恆顯示 0 筆（自審實測踩到）；覆蓋層優先於櫃檯值，且服務層 `try/finally` 保證清除（拋錯也要清，否則整個行程都被未採用的規則汙染）。
