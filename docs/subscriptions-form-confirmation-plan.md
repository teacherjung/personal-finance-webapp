# 訂閱表單成功後確認與呈現順序

## 來源與單一目的

本案承接原第 24 項的一個已證反例：A 表單寫入成功但回應晚到，取消 A 視窗後 B 標記已完成；A 的續行另起讀取並取代 B 的頁面、按鈕及通知，焦點落至 BODY。原反例是合成操作，兩筆 PUT 成功，沒有重複寫入或資料遺失的證據。正常儲存回到標題不列為缺陷。

原範圍依 [實際 Sol 技術裁示](https://github.com/teacherjung/personal-finance-webapp/pull/722#issuecomment-6281343888)；最小待確認設計依 [GPT‑6.1 Sol／xhigh 完整答覆](https://github.com/teacherjung/personal-finance-webapp/pull/722#issuecomment-6283204308)及[標準配對](https://github.com/teacherjung/personal-finance-webapp/pull/722#issuecomment-6283204674)。銀行前支 [#723](https://github.com/teacherjung/personal-finance-webapp/pull/723) 已合併、收樹並完成乾淨交接後才開本案。

目的只有一個：表單成功的事實可以重新確認，較舊表單不得因此取代較新的呈現。修正不能擴大成完整訂閱寫入排序、逐筆資料合併或跨視窗一致性框架。

## 狀態與資格

- 表單接受送出、等待 PUT／POST 前捕捉當前呈現資格；不能在成功回應後重新取得 owner。正常成功沿既有視窗所有權及正常交棒處理，使用者取消或新窗接管不能視為正常交棒。
- 表單成功事實使用模組私有的成功版次。每次真正取得既有 API 成功結果才記一次，寫入失敗不記；不保存 payload，也不把回應插回模型。
- 每個實際 GET 回合開始前記其涵蓋的成功版次。只有具資格且成功交付的讀取才消化涵蓋部分。後到的成功不能被較早讀取、錯誤或 finally 清掉。
- 標記、刪除及表單各守自己的確認語意；不借 flagConfirmationRevision、flagWriteTails 或刪除確認帳承載完整表單。

## 較舊成功的處置

舊 A 不自動 GET、不寫過期成功 toast、不替換 B 頁殼、列鈕或成功通知，也不移焦。必要提示是獨立的待確認狀態，文字採「資料已儲存，請重新載入確認更新」，按鈕沿既有「重新載入」文字及樣式。這句只說需要確認，不宣稱 B 的資料必定未更新。

提示只接到目前有效的訂閱頁，核對頁面、host、連線、路由／導覽序號、完整 hash 及讀取資格。空列表也要有合法頁面登記；既有刪除同步不能把新提示當一般注意訊息刪掉，亦不能因待確認而復活已刪列。

其他視窗開著或不在訂閱頁時，只保留最小成功事實，不插提示、不關窗、不聚焦。回到訂閱的新讀取可以確認；留在原頁但新窗已關閉時，仍須有可見的確認途徑。需要恢復觀察時，由當前頁持有最多一份有限觀察，交付提示、狀態消化或頁面失效即清理，不增加永久全域框架。

## 使用者重讀與既有資料維護接縫

重新載入是新的使用者讀取，不重送原 PUT／POST。等待期間按鈕不重複啟動；較舊完成不得解除較新讀取的停用狀態。成功交付涵蓋的結果才撤提示；失敗仍可重試。按鈕移除後的鍵盤焦點須有有限落點與一次性資格，外部移焦、新窗、換頁及較新操作優先，不泛改全站焦點策略。

訂閱讀取鏈的 autoExpire 與 freezeCompletedMonths 可能寫入資料。若成功版次已證明該讀取早於新成功，不再把已知過期快照送進尚未開始的自動維護寫入。沿既有資格檢查拒收失效結果，保留有效頁面及待確認狀態；沒有可保留頁面時，仍由具資格的讀取交付可重新載入的終態，不永久停在 loading、不自動循環 GET。

已經在途的自動寫入與同筆表單衝突不在本案重造排序；若另取得具體反例，保存輸入、實際操作、請求及回讀後交 Sol 裁定。本計畫不聲稱這類落庫缺陷已成立或已修好。

## 有限驗證

每題獨立種合成資料，驗到實際操作後才斷言保存，不沿用前題狀態。

| 情境 | 必要見證 |
|---|---|
| A 已寫入，成功回應晚於 B 呈現 | A／B 真操作及次數；B 頁面、列鈕、通知身分與焦點；舊 A 不追加 GET。 |
| A 實際寫入晚於 B 已讀完 | 分開寫入前與回應前屏障；使用者重讀後能確認 A 新值，不靠假造回應。 |
| 讀取在途又到表單成功 | 較早讀取不清新狀態；連續成功也不被舊回合清掉或解鎖。 |
| 失敗與重試 | PUT／POST 失敗不記成功；已成功但 GET 失敗仍有入口，重試只讀、不重寫。 |
| 空列表、刪除與標記接縫 | 提示不漏、不被刪除同步誤清、不復活已刪列；既有標記及刪除順序保持。 |
| 新窗、換頁及焦點 | 新窗內容與焦點保持，關閉後可確認；換頁回來新讀取接手；外部移焦不被搶回。 |
| 正常新增、編輯 | 真表單提交與讀回；既有可空資訊、日期、金額、週期、分類及控制列保存。 |
| 自動資料維護 | 能辨識的過期快照不得新啟動維護寫入；不把避開維護的種子說成全部交錯已驗。 |

合成 DOM 負責精確節點與焦點；有限 LOCAL HTTP 負責實際 CRUD 與回讀。正式 HTTP 只連本題獨立合成庫，不接真實財務資料。需新增或調整的回歸先在未修版於指定斷言紅，反控先基準綠、assert 替換目標、保留 A／B 操作，在相應保存斷言紅，再還原綠。至少分別破壞舊續行資格、成功版次保存及可用確認途徑；語法或環境失敗不算有效反控。

## 驗收方式

1. 先儲存一份訂閱表單，再讓另一個操作或視窗接手；舊成功回來時，較新的畫面與焦點保持。
2. 遇到待確認提示，重新載入可看見已儲存資料；失敗仍能重試，而且不會再次儲存原表單。
3. 核對一般新增、編輯、標記、刪除及空清單操作仍可用；開關視窗、切頁與外部移焦不被舊回覆接管。
