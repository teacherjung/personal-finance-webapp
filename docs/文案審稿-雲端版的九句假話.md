# 文案審稿：雲端版的九句假話

> **這份要 William 審。** Claude 起草、老師審改（專案鐵則）。
> 建立 2026-07-29。改完之後由 Claude 實作，**不要直接改程式**——有些句子牽涉模式判斷。

## 這份在講什麼

app 現在有兩種跑法：

- **本機版**：資料在你的 Mac 上（`data/store.db`）
- **雲端版**：資料在 Supabase，別人也會用

問題是**畫面上有九句話是照「只有本機版」的年代寫的**，在雲端版全部變成假話。
使用者是在「要不要把身分證字號交出來」「要不要按下不可逆的整批改名」這種時刻讀到它們的。

分兩類，**第二類比第一類嚴重**。

---

## 第一類：隱私承諾（5 句）

說「只存這台電腦」，但雲端版其實存在 Supabase。

| # | 位置 | 現在的話 | 在雲端版為什麼是假的 |
|---|---|---|---|
| 1 | 卡片編輯窗 | 帳單 PDF 密碼（**只存這台電腦、永不上傳**） | 會上傳，存在雲端資料庫（**有加密**） |
| 2 | 設定頁·證券 | …只存這台電腦、永不上傳，比照信用卡帳單密碼 | 同上 |
| 3 | 資產頁·帳戶 | 完整帳號（選填，**只存這台電腦**） | 會上傳，而且**沒有加密**（你 2026-07-29 裁決先不加密） |
| 4 | 設定頁·備份 | 所有資料**只存在本機** `data/store.db` | 雲端版資料在 Supabase |
| 5 | 收支頁·上傳 | 對帳單密碼（只在這台電腦解密、不會上傳、**不會儲存**） | ⚠️ **這一句其實是真的**——那個欄位是每次上傳現填、用完就丟。只有「這台電腦」的講法要調整 |

### 草稿

**1. 卡片 PDF 密碼**
- 本機版：`帳單 PDF 密碼（只存這台電腦、永不上傳）` ← 不動
- 雲端版：`帳單 PDF 密碼（加密後存在你的帳號裡，只有你看得到）`

**2. 證券對帳單密碼**
- 本機版：不動
- 雲端版：`存起來後上傳對帳單就不用每次輸入。密碼會加密後存在你的帳號裡。不存也可以——每次上傳時再輸入。`

**3. 完整帳號** ⚠️ 這一句最需要你決定語氣
- 本機版：`完整帳號（選填，只存這台電腦）` ← 不動
- 雲端版（誠實版）：`完整帳號（選填，存在你的帳號裡；用來把銀行對帳單對到這個帳戶）`
- 雲端版（更誠實版）：`完整帳號（選填，存在你的帳號裡、未加密；只用來把銀行對帳單對到這個帳戶）`

> **為什麼要你選**：你裁決了「先不加密」。要不要把「未加密」三個字寫出來，是產品判斷——
> 寫了比較誠實，但也可能讓人不敢填（不填的話銀行對帳單就配不到帳戶）。
> 我的建議是**不寫「未加密」**，因為對一般使用者來說那三個字只會製造焦慮、
> 卻沒有可行動的意義（他不能選擇加密）。但這是你的決定。

**4. 設定頁·備份說明**
- 本機版：不動
- 雲端版：`你的資料存在雲端資料庫，每天自動備份。建議偶爾自己匯出一份存著（匯出格式為 JSON）。`
  - ⚠️ **一定要補一句**：雲端版匯出的檔案**不含** IB 憑證與 PDF 密碼（刻意的），
    還原之後那幾樣要重新輸入一次。不講的話，使用者會以為「我有備份」。
  - 建議完整版：`你的資料存在雲端資料庫，每天自動備份。你也可以自己匯出一份存著——但匯出的檔案不含 IB 憑證與帳單密碼（為了安全刻意拿掉），還原後要重新輸入一次。`

**5. 收支頁上傳密碼** — 只改「這台電腦」的講法
- 兩種模式共用：`對帳單密碼（只用來解開這次上傳的檔案，不會儲存）`

## 第二類：安全網承諾（4 句）⚠️ 這一類比較嚴重

說「儲存前會自動備份」，但**雲端版根本沒有備份這個動作**
（`lib/repo.js:245`：雲端模式直接回 `false`，不備份、也不報錯）。

**為什麼比第一類嚴重**：使用者是在按下**不可逆**的動作之前讀到這句話的——
整批改名、刪分類、套用店名規則到所有舊記錄。他會想「反正有備份」然後按下去。

| # | 位置 | 現在的話 |
|---|---|---|
| 6 | 設定頁·支出分類 | 改名會自動套用到所有舊交易…**儲存前自動備份** |
| 7 | 設定頁·收入分類 | 同上 |
| 8 | 設定頁·店名規則 | 套用前會另存一份還原檔 `data/store.db.pre-rules.bak` |
| 9 | 店名規則面板 | 規則對**全部**記錄生效…**儲存前自動備份** |

### 草稿

**6／7／9（分類與規則的「儲存前自動備份」）**
- 本機版：`儲存前自動備份。` ← 不動
- 雲端版：`這個動作會改到所有舊記錄，而且**沒辦法還原**。請先按「預覽影響」確認。`

**8（店名規則的還原檔）**
- 本機版：`（套用前會另存一份還原檔 data/store.db.pre-rules.bak）` ← 不動
- 雲端版：`（這個動作沒辦法還原，請先預覽）`

> 💡 **我的建議**：這一類**不要等其他文案一起改**。就算你對第一類還沒想好，
> 第二類也該先修——因為它會讓人在錯誤的安全感下按不可逆的按鈕。

## 需要你決定的三件事

### ① 語氣：要不要提「加密」「未加密」這些字？

- **A. 完全不提技術**：「存在你的帳號裡，只有你看得到」
- **B. 提加密**：「加密後存在你的帳號裡」（我草稿用的）
- **C. 連未加密也講**：完整帳號那句寫出「未加密」

我建議 **B**：對「身分證字號」這種東西，講「有加密」是使用者真的想知道的；
但帳號那句不提「未加密」（見上面的理由）。

### ② 要不要加「可展開的詳細說明」？

專案有一條鐵則：「懂了才不會誤會的概念，一律在網頁上就地白話解釋」。
資料放哪、誰看得到，算不算那種概念？

- **A. 只改句子**（最小改動）
- **B. 句子 ＋ 一個「詳細說明」連結**，點開講清楚「資料在哪、誰看得到、我們做了什麼保護」

我**沒有替你決定**——那條鐵則原文限定在「否則會把正常數字當成算錯」的概念，
資料放哪不完全屬於那一類。這是你的產品判斷。

### ③ ⚠️ 一句我建議現在**不要寫**的話

草稿裡我刻意**沒有**寫「別的使用者看不到你的資料」這種話，即使那是我們的設計目標。

原因：那件事**還沒被證明**。跨使用者隔離目前只有「模擬資料庫」的考題，
真正算數的驗收（拿 A 的登入憑證直接打資料庫讀 B 的資料）**要等 C6 對抗腳本跑過真的 Supabase**——
而那支腳本今天才剛修好兩個假綠。

**在那之前，文案只寫已經證明的部分**（要登入才進得來），不寫資料庫層的隔離。
等驗收過了再加，那時候是有憑有據的。

## 技術附註（給 Claude 自己，你不用看）

前端目前**完全不知道自己跑在哪個模式**（`grep hosted public/` 零命中），所以「依模式顯示不同句子」需要先牽一條線。兩個選項：

- **A. 後端加旗標**：`/api/settings` 回應多一個布林。⚠️ 必須**只在 HOSTED 送出**，否則會改到 LOCAL 的 API 回應形狀，撞到「LOCAL 零改動」契約。
- **B. 用網址判斷**：LOCAL 把 SPA 掛在 `/`、HOSTED 掛在 `/finance`，所以 `location.pathname` 現成可用、零後端改動。比較 hacky，但不會碰到契約。

實作時一併補考題：**九處文案在 HOSTED 模式下不得出現「只存」「這台電腦」「自動備份」**。
