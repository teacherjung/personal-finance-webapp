## 〇、先看懂這一步在幹嘛

前面 C1–C5 都只是「repo 裡的程式」，`NOTEASY_HOSTED` 沒設＝你的本機一行都沒變。
C6 是**第一次真的把它放到網路上**，然後用一份攻擊清單去打它，看隔離是不是真的成立。

為什麼非做不可：C4b／C5 的自動考題用的是「模擬的假 Postgres」。它證明得了
「我們的程式在正確的資料庫語意下不會洩漏」，但證明不了「Supabase 上的 RLS 政策真的寫對了」。
**那一題只有打到真的資料庫才算數**，所以一直誠實地押後到這裡。

## 一、建 Supabase 專案（約 10 分鐘）

1. 到 supabase.com 登入 → **New project**
   - Name：`noteasy`
   - Database Password：**用密碼管理器產一組長密碼存好**（這是資料庫的 root 密碼，之後幾乎用不到，但掉了很麻煩）
   - Region：**Southeast Asia (Singapore)**（跟 Render 同區，延遲最低）
   - Plan：Free
2. 專案建好後，左邊 **SQL Editor** → New query → 把 repo 裡 `db/supabase-schema.sql` **整份貼上** → Run。
   - 應該看到 `Success. No rows returned`。
   - 這份 SQL 是**冪等**的（可以重複跑），日後改結構就是回來重跑一次。
3. 左邊 **Authentication → Providers → Email**：
   - **Enable sign ups：關掉**（邀請制，裁決③）
   - Confirm email：開著
4. **Authentication → URL Configuration**：
   - Site URL：先留空或填 Render 網址（第三步拿到之後回來補）
   - Redirect URLs：之後把 `https://<你的 Render 網址>/auth/confirm` 加進白名單（**不加會被擋**）
5. 左邊 **Project Settings → API**，抄下兩個值備用：
   - **Project URL**（`https://xxxxxxxx.supabase.co`）
   - **anon public** key
   - ⚠️ 同一頁還有一個 **service_role** key。**那一把不要複製、不要貼到任何地方**——
     它會繞過 RLS，等於萬能鑰匙。程式碼裡一處都沒有用到它（有自動考題盯著）。

## 二、產生機密主金鑰（10 秒）

在你的 Mac 終端機跑：

```bash
openssl rand -base64 32
```

輸出那一長串就是 `NOTEASY_MASTER_KEY`。**存進密碼管理器**。

它是用來加密 IB token 與 PDF 密碼（＝身分證字號）的鑰匙。
掉了的話資料不會壞，但那兩個欄位會變成「未設定」，要重新輸入一次。

## 三、建 Render 服務（約 10 分鐘）

1. 到 render.com 登入（用 GitHub 登入最方便，順便就授權好 repo 存取）
2. **New → Blueprint** → 選 `teacherjung/personal-finance-webapp` → 它會自動讀到 `render.yaml`
3. 它會逐一問你四個環境變數，照下面填：

| 變數 | 填什麼 |
|---|---|
| `SUPABASE_URL` | 第一步抄的 Project URL |
| `SUPABASE_ANON_KEY` | 第一步抄的 **anon public** key（**不是 service_role**） |
| `SITE_ORIGIN` | 先隨便填 `https://example.com`，服務建好拿到真網址後回來改 |
| `NOTEASY_MASTER_KEY` | 第二步 `openssl` 產生的那一串 |

4. Apply → 等它 build＋deploy（第一次約 3–5 分鐘）
5. 拿到網址（像 `https://noteasy-xxxx.onrender.com`）之後：
   - 回 Render **Environment** 把 `SITE_ORIGIN` 改成那個網址 → 存檔會自動重新部署
   - 回 Supabase **URL Configuration** 把 `https://noteasy-xxxx.onrender.com/auth/confirm` 加進 Redirect URLs

**驗證服務活著**：瀏覽器打開 `https://<網址>/health`，應該看到 `{"ok":true}`。
打開首頁應該是公開站；打開 `/finance` 應該被轉去 `/login`。

> ⚠️ Free 方案 15 分鐘沒人用會睡眠，下次打開要等 30–60 秒冷啟動。測試期正常，正式上線再升 Starter。

## 四、建兩個測試帳號（合成資料用）

**Authentication → Users → Invite user**，寄給兩個你收得到的信箱（Gmail 的 `+` 別名很好用）：

- `你的信箱+c6a@gmail.com`
- `你的信箱+c6b@gmail.com`

收信 → 點連結 → 設密碼（各設一組，記到密碼管理器）。
這兩個帳號是**攻擊測試專用**，之後可以直接刪掉。

⚠️ **不要用你自己的正式帳號跑對抗測試**——腳本會寫入資料。

## 五、跑對抗審查（約 2 分鐘）

在 repo 目錄跑：

```bash
export C6_BASE_URL="https://noteasy-xxxx.onrender.com"
export C6_A_EMAIL="你的信箱+c6a@gmail.com"
export C6_A_PASSWORD="A 的密碼"
export C6_B_EMAIL="你的信箱+c6b@gmail.com"
export C6_B_PASSWORD="B 的密碼"
export C6_SUPABASE_URL="https://xxxxxxxx.supabase.co"
export C6_SUPABASE_ANON_KEY="eyJ…（anon public）"
export C6_CONFIRM_SYNTHETIC=1
node scripts/c6-adversarial.js
```

它會逐條印出 ✅／❌。**任何一條 ❌ 都不可以進 C7**（不要把真實資料匯上去），
把輸出整段貼給 Claude 修。

九組考題分別是：

| # | 考什麼 | 為什麼重要 |
|---|---|---|
| ① | 未登入打全部 `/api/*` → 401；`/finance` → 轉登入 | 前端隱藏不算防禦 |
| ② | A 的 cookie 逐條打 30 個讀取端點 → 看不到 B 的任何東西（**兩個方向**） | 這是整套系統的核心承諾 |
| ③ | A 拿 B 的 id 做 PUT／DELETE → B 一筆都不能少 | 讀不到不代表改不到 |
| ④ | 偽造 cookie → 401（不是 500）；跨站 POST → 403 | 500 代表錯誤處理有洞 |
| ⑤ | **RLS 直連**：拿 A 的 token 直打 Supabase REST | **只有這一關證明得了 RLS 真的寫對** |
| ⑥ | 機密投影逐端點（含寫入端回應） | 本 repo 踩過 POST/PUT 回應洩漏的前例 |
| ⑦ | 錯誤訊息不含伺服器路徑／堆疊 | |
| ⑧ | A 匯入一份指名 B 的備份 → B 一個字都不變 | |
| ⑨ | 超大／畸形上傳 → 明確拒絕，服務不能掛 | |

跑完之後，**同一份清單也請 Codex 用 gpt-5.6-sol／xhigh 獨立再審一次**（見 `CODEX-REVIEW.md`）——
自動腳本只驗它想得到的攻擊，人（或另一個模型）想得到的往往不一樣。

## 六、⚠️ 上線前必須知道的三件事（Claude 的誠實回報）

### 1. 兩個依賴有安全通報，其中一個**目前無修可用**

`npm audit` 的現況（2026-07-27）：

| 套件 | 嚴重度 | 問題 | 有沒有修 |
|---|---|---|---|
| **xlsx**（SheetJS） | **high** | 原型污染（GHSA-4r6h-8v6p-xvw6）＋正規表示式 DoS（GHSA-5pgg-2g8v-p4x9） | ❌ **npm 上沒有修好的版本** |
| **fast-xml-parser** `<5.7.0` | moderate | XMLBuilder 的註解／CDATA 注入（GHSA-gh4j-gqv2-49f6） | ✅ 有，但要升到 5.x＝**breaking change** |

**Claude 的判斷與建議**：

- **xlsx**：這是「無修可用」的那一個。要點是**它從哪裡吃資料**——本專案只用它讀
  **你自己上傳的** Excel／對帳單，不吃網路上的檔案。所以攻擊前提是「你自己上傳一個惡意檔案」，
  與 C0 威脅模型裡「使用者自己匯入惡意備份」同一級。多人化之後風險**沒有**放大
  （每個人只能上傳給自己看），但兩件事值得做：
  ①**上線前確認上傳端點有大小與解析上限**（C6 考題⑨會驗）
  ②官方修好的版本只在 SheetJS 自家的 registry（`https://cdn.sheetjs.com`）發佈，
  **要不要改用自家 registry 是需要你拍板的事**（會多一個非 npm 的相依來源）。
  在你拍板之前，現況＝**記錄在案、不擋上線**（AGENTS.md 早就寫了這一條）。
- **fast-xml-parser**：這個**有修**，但要升大版本。它只用來解析 **IBKR Flex XML**（你自己的報表），
  而且我們只**讀**不**寫** XML——那個 advisory 講的是 `XMLBuilder`（寫），**我們沒有用到**。
  所以風險實際上是零，但既然有修，建議**另開一支小 PR 升版＋跑回歸**，不要夾在階段 C 裡。

> `npm audit` 也建議進 CI（C0 的 P2 清單第 4 條），目前還沒做。

### 2. Supabase Free 沒有自動備份，而且一週沒活動會暫停專案

- **沒有自動備份**（Pro US$25/月才有 7 天）。C0 已記錄，替代方案＝雲端版每日排程匯出 JSON。
  ⚠️ 但 C5 之後**雲端匯出不含機密**，所以那份備份還原後要重輸 IB token 與 PDF 密碼——這是刻意的。
- **一週無活動會暫停專案**。測試期可接受；正式上線前要評估升級或設一個定期喚醒。

### 3. ~~有一個「需要你拍板」的契約點還沒改~~ → **已修（2026-07-28，William 指示）**

**JSON body parser 原本掛在 auth 牆之前**（`server.js`），等於「不管誰寄來的包裹都先全部拆開，
拆完才到櫃台問這個人能不能進來」。

實測（模擬 Render 512MB 容器，`--max-old-space-size=400`）：

| | 10 個未登入請求 × 45MB | 伺服器 |
|---|---|---|
| **修之前** | 全部無回應 | ❌ **DEAD**（`FATAL ERROR: Reached heap limit`） |
| **修之後** | 全部 401，耗時 550ms | ✅ **ALIVE** |

修法＝把 `installJsonBodyParsers(app)` 搬到 `authGate` 之後，牆前只留一個 32KB 的
`/api/auth` 專屬 parser（登入要讀信箱密碼）。**LOCAL 的位置完全沒動**。

口徑變化（唯一的）：未登入者送壞 JSON／超大 body，回應從 400／413 變成 **401**——
這其實更正確：身分牆本來就該先發言，而且不再對未登入者洩漏「哪些網址的 body 上限比較大」。

## 七、C6 通過之後 → C7（真實資料上線）
